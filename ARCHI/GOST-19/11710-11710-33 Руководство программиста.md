# Руководство программиста

**Обозначение:** 11710-11710-33
**Наименование программы:** «Платформа АРХИ» — система управления строительными проектами и регламентами с использованием семантического искусственного интеллекта
**Стандарт:** ГОСТ 19.504-79 «Единая система программной документации. Руководство программиста. Требования к содержанию и оформлению»
**Дата:** 2026-09-01
**Адресат документа:** бизнес-аналитик по регламентам

## Аннотация

Документ содержит сведения, необходимые бизнес-аналитику для описания, проверки и ввода в работу регламентов на предметно-ориентированном языке Flow DSL средствами Платформы АРХИ, реализованной на платформе РАГРАФ (развёрнутый экземпляр — https://ragraf.up.railway.app).

**Полное описание языка вынесено в комплект фреймворка:** `00000-00000-35 Описание языка` (ГОСТ 19.506-79), каталог `docs/RAGRAF/GOST-19/`. Там — исчерпывающий перечень типов узлов и их параметров, грамматика выражений и встроенные функции, семантика исполнения, средства отладки, обмен данными и разбор учебных примеров. Язык принадлежит доменно-нейтральному ядру и одинаков для всех платформ, поэтому настоящий документ его не повторяет, а описывает работу методолога **на строительной предметной области**.

Изложены: назначение и условия применения программы; полная характеристика языка регламентов — типы узлов, их поля и семантика исполнения; язык формул с трёхзначной логикой; порядок обращения к программе через интерфейс и программный интерфейс; состав входных и выходных данных; полный перечень сообщений с указанием действий аналитика по каждому.

**Почему адресат руководства — бизнес-аналитик.** ГОСТ 19.504-79 определяет руководство программиста как документ для лица, которое **само задаёт логику работы программы**, в отличие от оператора, который эту логику лишь применяет. В Платформе АРХИ логика контроля не зашита в исходный код: регламент — приказ, свод правил, пункт договора — переносится в систему как цифровой двойник регламента (ЦДР) и описывается на предметно-ориентированном языке Flow DSL — графом из типизированных узлов и связей. Этот граф исполняет детерминированный интерпретатор — ядро исполнения (`backend/app/services/flow_executor.py:126`). Изменение правила означает изменение графа, а не изменение программы: цикл разработки, сборки и выпуска новой версии системы не требуется.

Отсюда роль бизнес-аналитика: он пишет на формальном языке (Flow DSL с фиксированным множеством типов узлов, полей и правил вычисления), отвечает за корректность алгоритма (раздел 2.8), отлаживает правило на тестовых данных с пошаговой трассой (раздел 3.1, шаг 5), управляет версиями своих правил (раздел 3.3) и обрабатывает сообщения об ошибках (раздел 5) — то есть выполняет ровно те действия, для которых ГОСТ 19.504-79 и предусматривает настоящий вид документа. Аналитик при этом **не является разработчиком системы**: он не имеет доступа к исходному коду платформы, не выполняет сборку и развёртывание, не может выполнить произвольный код — вычислитель формул допускает только выражения из закрытого перечня конструкций (раздел 2.5). Настоящий документ — руководство по языку регламентов, а не по устройству платформы. Устройство серверной части и порядок её обслуживания изложены в документе 11710-11710-32 «Руководство системного программиста».

Документ описывает **только реализованную функциональность**. Основание — техническое задание, редакция 8.0 (обозначение 11710-11710-1), раздел 4. Требования, вынесенные в приложение А указанного ТЗ «Требования, отнесённые к развитию платформы», в настоящем руководстве как реализованные не описаны.

## 1. Назначение и условия применения программы

### 1.1. Назначение программы

Программа предназначена для перевода нормативных и организационно-распорядительных документов строительного проекта в исполняемые цифровые двойники регламентов, для автоматического исполнения этих регламентов по поступающим событиям и для выдачи вердикта с доказательной трассой вычисления.

Аналитик решает программой следующие задачи:

1. создание регламента из текста нормативного документа;
2. описание логики правила на языке Flow DSL;
3. статическая проверка правила на непротиворечивость и полноту;
4. отладка правила на тестовых значениях;
5. задание критерия решённости — условия, по которому система сама проверяет, исполнен ли регламент;
6. связывание регламентов в цифровой двойник процесса;
7. публикация версии регламента и выгрузка его семантического представления.

### 1.2. Условия применения

| Условие | Значение |
|---|---|
| Рабочее место | персональный компьютер, современный браузер (Windows, macOS, Linux) |
| Доступ к серверной части | по протоколу HTTPS к развёрнутому экземпляру |
| Права | изменение — только после административного входа по единому паролю, кнопка «Войти как админ» в шапке (`backend/app/auth.py:91`); просмотр — без входа, при этом для доменов с закрытой калибровкой пороги и веса формул маскируются (`backend/app/api/flow.py:23`) |
| Разделы интерфейса аналитика | «Регламенты» (`/regulations`), редактор регламента (`/regulations/:id/edit`), редактор графа (`/regulations/:id/flow`), «Сима · Студия» (`/sandbox`), «Цифровой двойник» (`/twins`), «Триггеры» (`/sensors`), «Исполнение» (`/execute`), «Журнал прогонов» (`/audit-log`), «Свод противоречий» (`/conflicts`), «Методология» (`/methodology`), «Словарь терминов» (`/glossary`) |
| Программный интерфейс | REST, машиночитаемая спецификация — `/openapi.json`, интерактивная документация — `/docs` |

### 1.3. Ограничения применения

Аналитик работает в границах реализованной функциональности. В частности, средствами языка регламентов **нельзя**: обратиться к системам Oracle Primavera, Microsoft Project, Redmine, 1С и системам электронного документооборота; прочитать информационную модель здания в формате IFC (приложение А ТЗ 8.0, п. А.1); подписать вердикт электронной подписью; разграничить права по проектам (приложение А ТЗ 8.0, п. А.6); принять входящее сообщение из мессенджера (приложение А ТЗ 8.0, п. А.3). Интеграция с системой управления проектами одна — Plan-R, и она работает **на чтение**.

Отдельно: **задача в трекере по срабатыванию регламента автоматически не заводится**. Ни один поставляемый регламент задачу не создаёт; задача заводится человеком из карточки вердикта (раздел «Исполнение»). Причина изложена в приложении Б настоящего руководства. Автоматическое заведение задачи по срабатыванию регламента для поставляемых регламентов отнесено к развитию платформы (приложение А ТЗ 8.0, п. А.7).

Перечисленное в настоящем руководстве как имеющееся не описывается.

## 2. Характеристика программы

> **О соотношении с описанием языка.** Подразделы 2.2–2.9 — рабочая выдержка, собранная для того, чтобы методолог держал нужное под рукой, не открывая второй документ. Исчерпывающее и **преимущественное** описание языка — документ **00000-00000-35 «Описание языка»** комплекта фреймворка (ГОСТ 19.506-79). При расхождении верным считается он. Настоящий документ описывает работу методолога на строительной предметной области; сам язык принадлежит ядру и одинаков для всех платформ.

### 2.1. Общее устройство

Регламент проходит пять слоёв: шлюз событий → ядро исполнения → хранилище цифровых активов → интеграционный слой → интерфейс. Аналитик программирует второй слой — ядро исполнения — и задаёт контракт данных для первого.

Цифровой двойник регламента состоит из **паспорта** — наименование, домен, версия, статус, документ-основание, пункт документа, срок действия (`backend/app/schemas/domain.py:173`); **параметров** — контракт данных одного входа: тип, эталон, допуск, границы, единица измерения, обязательность (`domain.py:15`); **графа Flow DSL** — узлы и связи (`domain.py:464`); **критерия решённости** — машинно-проверяемое условие исполнения (`domain.py:50`); **триггеров** — декларация «вход регламента ← источник события» (`domain.py:118`).

### 2.2. Структура программы на языке Flow DSL

Граф хранится как объект с полями `rule_id`, `regulation_id`, `nodes`, `edges`. Узел (`backend/app/schemas/domain.py:386`) имеет обязательные поля `id` и `type`, необязательные `label` и `position`, и набор полей, значимых для конкретного типа. Связь (`backend/app/schemas/domain.py:458`) имеет поля `source`, `target` и необязательное `condition`. Идентификатор связи в трассе и подсветке — `source__target`.

Граф обязан быть ациклическим: цикл отвергается проверкой `CYCLE_DETECTED`.

### 2.3. Типы узлов и их поля

Перечень типов задан в `backend/app/schemas/domain.py:342`. Названия в палитре редактора приведены по `frontend/src/lib/api.ts` (`NODE_KIND_META`).

| Тип | Название в редакторе | Назначение | Значимые поля |
|---|---|---|---|
| `sensor` | Событие | Точка входа в поток: внешний сигнал либо выход другого регламента | `sensorType`, `sensorSubtype`, `bindsTo`, `externalId`, `sourceKind`, `sourceRegulationId`, `sourceOutputAction`, `leykaTrigger` |
| `time` | Время | Источник-условие по системным часам; входной связи не имеет | `expression`, `timeMode` |
| `input` | Вход | Хранит значение одного параметра регламента | `paramRef` |
| `threshold` | Порог | Решение «эталон ± допуск» по одной величине | `refValue`, `deviation`, `unit` |
| `compare` | Сравнить | Сравнение значения с эталоном или двух значений между собой | `operator`, `refValue`, `deviation` |
| `formula` | Формула | Произвольное выражение над параметрами | `expression` |
| `switch` | Развилка | Маршрутизация ровно в одну ветку по числовым зонам | `cases` — список `{value, label, min?, max?}` |
| `output` | Выход | Действие и рекомендация; несёт уровень критичности | `action`, `text`, `priority`, `leykaTaskId`, `leykaTaskUrl` |
| `shacl_constraint` | SHACL | Проверка значения против формального ограничения регламента | `constraintRef` |

Пояснения по полям, важные при написании правил:

- `bindsTo` — идентификатор узла «Вход», в который узел «Событие» подаёт значение. Без него узел «Событие» игнорируется ядром исполнения. При сохранении графа платформа автоматически привязывает узел «Событие» с заданным подтипом к ближайшему по вертикали свободному входу (`backend/app/api/flow.py:55`).
- `paramRef` — идентификатор параметра регламента; он же служит именем переменной в формулах.
- `priority` — уровень критичности вердикта: `0` — норма; уровень результата вычисляется как **максимум** `priority` среди сработавших выходов (`backend/app/services/flow_executor.py:508`).
- `cases` — зоны развилки, граница полуоткрытая `min ≤ V < max`; зона без обеих границ — ветка «всё остальное». Ключ `condition` на исходящей связи развилки должен совпадать с `value` либо `label` соответствующей зоны.
- `leykaTaskId`, `leykaTaskUrl` — реквизиты задачи в трекере, которые заполняются **после ручного связывания** выхода с задачей (кнопка «Связать с LEYKA»); автоматическим заведением задачи по срабатыванию правила они не являются (см. приложение Б).
- `action` — обозначение предписанного действия. Оно не запускает автоматического исполнителя: перечень допустимых обозначений и порядок их применения — приложение Б.

### 2.4. Семантика исполнения

Ядро исполнения (`backend/app/services/flow_executor.py:126`) выполняет граф в следующем порядке.

1. **Разрешение входов.** Каждое измерение сопоставляется узлу «Вход» по одному из трёх правил, в порядке приоритета: по идентификатору узла «Событие» и его полю `bindsTo`; по идентификатору параметра; по типу датчика. Не сопоставленные измерения отбрасываются.
2. **Узлы «Событие».** Помечаются сработавшими, если для их `bindsTo` разрешено значение (`flow_executor.py:176`).
3. **Узлы «Вход».** Помечаются сработавшими при наличии значения (`flow_executor.py:192`).
4. **Узлы «Порог».** Значение берётся у непосредственного предшественника-входа, при его отсутствии — через один промежуточный узел. Условие срабатывания: `|значение − refValue| > deviation` (`flow_executor.py:225`). Порог без `refValue` или `deviation` не срабатывает никогда и сопровождается пояснением «порог не настроен».
5. **Узлы «Время».** Вычисляют своё выражение на системных часах и при истинном результате зажигают ветку так же, как сработавший порог (`flow_executor.py:257`).
6. **Распространение сигнала.** Обход графа в ширину от сработавших узлов. «Формула» вычисляется по-настоящему (`flow_executor.py:292`): булев результат зажигает ветку по истинности, числовой считается вычисленным при любом значении, включая ноль, и передаётся вниз. «Сравнить» вычисляется по пяти стратегиям в порядке приоритета (`flow_executor.py:839`): «вне диапазона» через порог-предшественник; «вне диапазона» по собственным `refValue` и `deviation`; одиночный оператор против `refValue`; двухместное сравнение двух предшественников; при неопределимости — сквозной проброс. «SHACL» сверяет значение предшественника с ограничением по `constraintRef` и считается сработавшим при нарушении (`flow_executor.py:940`). «Развилка» на первом проходе только накапливает пришедшие ключи (`flow_executor.py:350`).
7. **Маршрутизация развилок** (второй проход, `flow_executor.py:384`). Если у развилки есть входящая связь от узла «Время» и ни один такой узел не сработал — развилка пропускается целиком. Если пришедший ключ совпал с `condition` исходящей связи — активируется совпавшая ветка. Иначе, если у зон заданы числовые границы и на вход развилки пришло число, выбирается **ровно одна** ветка по правилу `min ≤ V < max` (`flow_executor.py:622`, условие — `flow_executor.py:660`); если значение не попало ни в одну зону, не активируется ни одна ветка. Если границ нет и ключи не совпали — активируются все исходящие связи (режим совместимости).
8. **Вердикт.** `level` = максимум `priority` среди сработавших выходов, `0` при их отсутствии; `recommendation` — тексты сработавших выходов через перевод строки; дополнительно возвращаются перечни сработавших узлов и связей, полная трасса и разрешённые входы.

Исполнение детерминировано: один и тот же граф на одних и тех же входах всегда даёт один и тот же вердикт.

### 2.5. Язык формул

Вычислитель (`backend/app/services/formula_eval.py`) разбирает выражение в синтаксическое дерево и обходит его по белому списку узлов (`formula_eval.py:120`). Произвольный код не исполняется; функции вызываются только по имени из закрытого перечня.

**Разрешено:** числовые и строковые литералы, `True`/`False`/`None`; арифметика `+ - * / % // **`; унарные `-x`, `+x`, `not x`; сравнения `== != < <= > >=`, в том числе цепочки вида `0 < x < 10`; `and`, `or`, `not`; тернарное `a if cond else b`; списки и проверка `x in [a, b, c]`; вызовы встроенных функций.

**Запрещено:** определения функций, лямбды, импорт, обращение к атрибутам и элементам по индексу, именованные аргументы, присваивание. Любая такая конструкция отвергается на разборе.

Для совместимости с записью в стиле языка C перед разбором выполняется замена `&&` → `and`, `||` → `or`, одиночного `!` → `not` (`formula_eval.py:167`).

**Встроенные функции** (`formula_eval.py:353`):

| Группа | Функции |
|---|---|
| Числовые | `abs`, `min`, `max`, `round`, `sqrt`, `pow`, `log`, `log10`, `exp`, `floor`, `ceil`, `sign` |
| Тригонометрия | `sin`, `cos`, `tan`, `asin`, `acos`, `atan`, `atan2` |
| Логика | `between(x, lo, hi)` |
| Время и календарь | `now()`, `hour()`, `minute()`, `day_of_week()` (понедельник = 0), `is_weekend()`, `is_night(начало, конец)` |
| Временные ряды | `rate(параметр, окно)`, `delta(параметр, окно)`, `prev(параметр)`, `mean(параметр, окно)`, `max_over(параметр, окно)`, `min_over(параметр, окно)`, `count_above(параметр, значение, окно)` |

Окно задаётся строкой «число + единица»: `"30m"`, `"1h"`, `"3d"`. **Константы** (`formula_eval.py:395`): `pi`, `e`, `inf`, `nan`, `True`, `False`, `None`.

Ограничения вычислителя: деление и взятие остатка на ноль отвергаются; показатель степени по модулю более 1024 отвергается.

**Трёхзначная логика при отсутствии данных.** Отсутствующее значение обозначается `None` и трактуется как «неизвестно» (логика Клини):

| Выражение | Результат |
|---|---|
| арифметика с `None` | `None` (`formula_eval.py:439`) |
| `неизвестно and истина` | `неизвестно` |
| `неизвестно and ложь` | `ложь` (`formula_eval.py:490`) |
| `неизвестно or истина` | `истина` |
| `неизвестно or ложь` | `неизвестно` (`formula_eval.py:500`) |
| `not неизвестно` | `неизвестно` |
| числовое сравнение с `None` | `неизвестно` (`formula_eval.py:527`) |
| `x == None`, `x != None`, `x in [...]` | вычисляются обычным образом — это проверка наличия значения |

Узел «Формула» с результатом «неизвестно» **не срабатывает** (`flow_executor.py:814`): система не выдаёт вердикт вместо того, чтобы выдать ложное «нарушений нет». В трассе указывается, каких именно переменных не хватило. Обязанность аналитика — предусмотреть ветку ручной проверки или эскалации на этот случай; отсутствие такой ветки диагностируется проверкой `UNKNOWN_INPUT_NO_FALLBACK`.

Приём для устойчивых формул: `rate("p", "1h") or 0` — подстановка нуля, когда истории ещё нет.

### 2.6. Контракт данных и семантическое представление

Параметр — единый источник правды контракта данных. Из его полей выводится форма ограничений SHACL при выгрузке (`backend/app/services/turtle_bridge.py:428`): `datatype` → `sh:datatype`, `required` → `sh:minCount`, `minInclusive`/`maxInclusive` → одноимённые ограничения, `pattern` → `sh:pattern`. Отдельного редактируемого слоя ограничений нет.

Регламент сериализуется в RDF/Turtle в собственной онтологии `http://regulations.local/ontology#` (`turtle_bridge.py:169`). Параметры записываются плоскими свойствами, допуск — парным свойством `<параметр>Deviation`. Дополнительно выгружаются: документ-основание по стандарту PROV-O (`prov:wasDerivedFrom`, ссылка, цитата, контрольная сумма), критерий решённости как узел `:AcceptanceCriterion`, действия при отрицательном результате, триггеры как узлы `:Trigger`. Обратный разбор Turtle в структуру регламента выполняет `turtle_bridge.py:648`.

### 2.7. Критерии решённости

Критерий — условие, по которому система сама проверяет, исполнен ли регламент. Задаётся на регламенте; помимо основного допускаются дополнительные, они объединяются по «И» (`backend/app/services/etl/applier.py:83`).

| Вид | Когда проверяется | Обязательные поля | Смысл |
|---|---|---|---|
| `no_violation` | сразу после прогона | — | уровень вердикта равен 0 |
| `specific_output` | сразу после прогона | `expected_output_id` | сработал выход с указанным кодом действия либо названием |
| `custom` | вручную | `text` | отметку ставит аналитик; автоматического закрытия по времени нет |
| `task_closed_within_sla` | отложенно | `sla_seconds` > 0 | задача по вердикту закрыта в срок; задача заводится из карточки вердикта вручную (автоматическое заведение — приложение А ТЗ 8.0, п. А.7; причина — приложение Б настоящего руководства) |
| `sensor_returned_normal` | отложенно | `sensor_subtype`, `sensor_field`, `normal_threshold`; необязательно `followup_seconds` (по умолчанию 1800 с) | через заданное время датчик показал значение ниже порога |

Отложенные критерии разрешает `backend/app/services/etl/acceptance_resolver.py:153` на каждом цикле сбора данных. Если критерий не разрешился за предельный срок (не менее 7 суток, для больших сроков — кратно им), он помечается непройденным по истечении срока. Правильность настройки критерия проверяется до сохранения (раздел 2.8, коды с префиксом `PRIMARY_` / `ADDITIONAL_<номер>_`).

Значение по умолчанию для домена «construction» — `no_violation` (`backend/app/services/default_criteria.py:116`).

### 2.8. Проверки правила: полный перечень кодов

Проверки выполняются в четырёх местах: структурная проверка графа (`backend/app/services/validator.py:67`), необязательные предупреждения при сохранении (`backend/app/services/flow_validators.py:74`), анализ непротиворечивости и пробелов (`backend/app/services/regulation_analysis.py:192`) и проверка критерия (`validator.py:482`). Ни одна из них не блокирует сохранение черновика; ошибки означают, что правило не будет работать так, как задумано.

| Код | Что означает | Как исправить | Уровень |
|---|---|---|---|
| `DANGLING_EDGE` | связь ссылается на несуществующий узел | удалить связь или восстановить узел | ошибка |
| `ISOLATED_NODE` | узел без единой связи | соединить узел с графом или удалить его | ошибка |
| `MISSING_INPUT` | нет ни одного узла «Вход» и ни одного узла «Время» | добавить источник значения | ошибка |
| `MISSING_OUTPUT` | нет ни одного узла «Выход» | добавить выход с действием и текстом | ошибка |
| `NO_IO_PATH` | ни от одного источника нет пути к выходу | соединить логику с выходом | ошибка |
| `CYCLE_DETECTED` | в графе обнаружен цикл | разорвать цикл; граф обязан быть ациклическим | ошибка |
| `UNKNOWN_PARAM_REF` | `paramRef` входа не найден среди параметров регламента | выбрать существующий параметр либо создать его на вкладке «Поля» | ошибка |
| `THRESHOLD_OUT_OF_BOUNDS` | `refValue` порога вне допустимых границ параметра | привести эталон в диапазон параметра или расширить границы параметра | предупреждение |
| `COMPARE_INSUFFICIENT_INPUTS` | у узла «Сравнить» нет входов либо один вход и он не порог | подключить порог либо добавить второй вход | предупреждение |
| `MISSING_CONSTRAINT_REF` | узел SHACL не ссылается на ограничение | указать `constraintRef` | ошибка |
| `UNKNOWN_CONSTRAINT_REF` | указанное ограничение не существует | выбрать существующее ограничение | ошибка |
| `FORMULA_SYNTAX` | выражение формулы или узла «Время» не разбирается | исправить выражение; проверить через «Проверить синтаксис» | ошибка |
| `SWITCH_ZONE_OVERLAP` | зоны развилки пересекаются — одно значение попадает в две ветки | выровнять верхнюю границу одной зоны и нижнюю следующей в одну точку | ошибка |
| `SWITCH_ZONE_GAP` | между соседними зонами дыра — значения не попадают никуда | состыковать зоны встык | предупреждение |
| `TIME_GATE_OVERLAP` | интервалы двух узлов «Время» на одной развилке пересекаются | сделать границы полуоткрытыми: час начала входит, час конца — нет | ошибка |
| `TIME_GATE_GAP` | ровно один час не покрыт ни одним интервалом времени | состыковать интервалы встык | ошибка |
| `DEAD_SWITCH_CASE` | ветка развилки целиком вне допустимого диапазона параметра — не сработает никогда | привести границы зоны в диапазон параметра либо расширить диапазон параметра | ошибка |
| `CONTRADICTORY_OUTPUTS` | выход «одобрить/норма» и выход «заблокировать/стоп» могут сработать на одном входе | развести взаимоисключающие выходы развилкой | ошибка |
| `SWITCH_UNCOVERED_RANGE` | значения на краях диапазона параметра не попадают ни в одну зону — вердикта не будет | добавить крайнюю зону либо ветку «всё остальное» | предупреждение |
| `UNKNOWN_INPUT_NO_FALLBACK` | правило решает по формулам, но не имеет ветки ручной проверки или эскалации на случай отсутствия данных | добавить выход с действием `request_manual_check` или `create_followup_task` | предупреждение |
| `DEAD_OUTPUT` | к выходу не ведёт ни один источник данных — исход не наступит | подключить выход к логике | ошибка |
| `UNREACHABLE_NODE` | вычисляющий узел не ведёт ни к одному выходу — не влияет на вердикт | подключить узел к выходу или удалить | предупреждение |
| `threshold_no_refvalue` | у порога не задан эталон — узел молча не срабатывает | заполнить `refValue` и `deviation` | предупреждение |
| `output_no_action` | у выхода нет кода действия — вердикт зафиксируется, но предписанное действие не определено | задать код действия из реестра (приложение Б) | предупреждение |
| `output_unknown_action` | код действия отсутствует в реестре действий (приложение Б) | исправить опечатку либо выбрать код из реестра; сообщение подсказывает близкие коды | предупреждение |
| `switch_no_cases` | у развилки не заданы зоны — исходящие связи не будут использованы | задать зоны с границами | предупреждение |
| `switch_edge_no_condition` | у исходящей связи развилки нет ключа маршрутизации | задать ключ либо оставить связь как ветвь по умолчанию | справка |
| `switch_edge_unknown_condition` | ключ на связи не совпадает ни с одной зоной | привести ключ к `value` или `label` зоны | предупреждение |
| `PRIMARY_MISSING_OUTPUT_ID` | у критерия `specific_output` не указан ожидаемый выход | указать код действия либо название выхода | ошибка |
| `PRIMARY_UNKNOWN_OUTPUT_ID` | указанный выход не найден среди выходов графа | выбрать существующий выход | предупреждение |
| `PRIMARY_INVALID_SLA` | у критерия `task_closed_within_sla` срок не задан или не положителен | задать `sla_seconds` больше нуля | ошибка |
| `PRIMARY_MISSING_SENSOR_FIELDS` | у критерия `sensor_returned_normal` не заполнены обязательные поля | заполнить подтип датчика, поле и порог нормы | ошибка |
| `PRIMARY_INVALID_FOLLOWUP` | отсрочка проверки не положительна | задать `followup_seconds` больше нуля | ошибка |

Коды с префиксом `PRIMARY_` относятся к основному критерию; для дополнительных критериев префикс — `ADDITIONAL_<номер>_`.

Отчёт вкладки «Проверка регламента» раскладывает найденное по трём корзинам: «Непротиворечивость» (`SWITCH_ZONE_OVERLAP`, `TIME_GATE_OVERLAP`, `CYCLE_DETECTED`, `DEAD_SWITCH_CASE`, `CONTRADICTORY_OUTPUTS`), «Пробелы» (`SWITCH_ZONE_GAP`, `TIME_GATE_GAP`, `SWITCH_UNCOVERED_RANGE`, `UNKNOWN_INPUT_NO_FALLBACK`, `UNREACHABLE_NODE`, `DEAD_OUTPUT`, `NO_IO_PATH`, `MISSING_OUTPUT`, `MISSING_INPUT`), «Прочие замечания» (остальные).

### 2.9. Цифровой двойник процесса

Цифровой двойник процесса — именованный набор регламентов со связями «выход одного — вход другого» (`backend/app/schemas/domain.py:515`). Связь описывается четырьмя полями: регламент-получатель, его параметр, регламент-источник, код действия выхода источника; пустой код действия означает «слушаю любой вердикт» (`domain.py:491`).

Правило двух уровней: регламент атомарен и ничего не знает о других; связи хранятся только в двойнике и при сохранении проецируются в графы регламентов-получателей — соответствующий узел «Событие» получает `sourceKind = "regulation"`, `sourceRegulationId` и `sourceOutputAction`.

Инварианты, проверяемые при сохранении (`backend/app/api/processes.py:36`): оба регламента связи входят в состав двойника; самоссылка запрещена; пара «регламент-получатель + параметр» не повторяется внутри двойника и не может принадлежать двум двойникам одновременно. При снятии регламента из состава связи на него удаляются автоматически.

## 3. Обращение к программе

### 3.1. Порядок работы аналитика

**Шаг 1. Создание регламента из текста документа.** Раздел «Регламенты» → «Создать из текста» (`/regulations/new-from-text`). Текст нормы отправляется на разбор (`backend/app/api/sandbox.py:537`); система извлекает числовые параметры вида «значение ± допуск единица», предсказывает предметную область и показывает до трёх похожих существующих регламентов. Аналитик отмечает нужные параметры и задаёт наименование; регламент собирается вместе со стартовым графом (`backend/app/api/sandbox.py:700`, `backend/app/services/templates.py:355`). Стартовый граф — по цепочке «Вход → Порог → Сравнить» на каждый параметр и один общий «Выход». Регламент создаётся в статусе «черновик», версия 0.1; допуск, не заданный явно, принимается равным единице (`backend/app/services/flow_storage.py:199`, `:249`).

**Шаг 2. Правка в форме параметров.** Карточка регламента (`/regulations/:id/edit`) имеет ровно пять вкладок (`frontend/src/components/regulations/RegulationEditorScreen.tsx:72`): «Поля», «Слайдеры», «Turtle», «Проверка регламента», «Проверка знаний». Блоки «История правок», «Документ-основание» и «Прогноз» размещены **внутри** вкладки «Поля». Граф исполнения открывается **отдельным экраном** по маршруту `/regulations/:id/flow` и вкладкой карточки не является.

Вкладка «Поля»: идентификатор и наименование параметра, тип, эталон, допуск, жёсткие границы, единица измерения, обязательность. Вкладка «Слайдеры» — калибровка допусков в границах, заданных ограничениями. Здесь же указываются документ-основание, пункт документа, срок действия, ответственная роль и требуемые компетенции. Оригинал документа прикрепляется файлом с подсчётом контрольной суммы (`backend/app/api/regulations.py:662`); целостность впоследствии сверяется отдельной операцией (`backend/app/api/regulations.py:752`).

**Шаг 3. Сборка графа.** Раздел `/regulations/:id/flow`. Узлы переносятся из палитры, свойства задаются на правой панели. При сохранении графа платформа: привязывает несвязанные узлы «Событие» к ближайшим свободным входам; выводит параметры регламента из входов и порогов; пересобирает триггеры; переносит текст и приоритет выхода в рекомендацию регламента; возвращает предупреждения проверки (`backend/app/api/flow.py:55`).

**Шаг 4. Проверка правила.** Вкладка «Проверка регламента» (`backend/app/api/regulations.py:415`) — непротиворечивость и пробелы. Отдельно проверяется критерий решённости (`backend/app/api/regulations.py:392`). Синтаксис отдельной формулы можно проверить и вычислить на пробных значениях, не сохраняя граф (`backend/app/api/formula.py:141`, `:164`); перечень доступных функций и констант выдаёт `backend/app/api/formula.py:200`.

**Шаг 5. Прогон на тестовых данных.** Панель «Запуск» редактора графа либо `POST /api/regulations/{id}/execute` (`backend/app/api/flow.py:365`). Допускается передать граф прямо в запросе и прогнать несохранённый черновик. Платформа умеет сама подобрать наборы входов, дающие каждый из уровней вердикта, — «Норма / Внимание / Критично» (`backend/app/api/flow.py:569`). Каждый прогон пишется в журнал прогонов с идентификатором инцидента.

**Шаг 6. Критерий решённости.** Задаётся в редакторе графа: якорный чип «◇ Критерий решённости» под схемой открывает панель настройки справа (`frontend/src/components/flow/CriterionEditorPanel.tsx`). Вид критерия и обязательные поля — раздел 2.7.

**Шаг 7. Публикация версии.** Перевод статуса в «активный» (`backend/app/api/regulations.py:474`). Активный регламент подхватывается планировщиком и исполняется по поступающим событиям. Обратный перевод — «архив» (`backend/app/api/regulations.py:487`).

## 4. Входные и выходные данные

### 4.1. Входные данные

| Данные | Формат | Назначение |
|---|---|---|
| Текст нормативного документа | обычный текст | извлечение параметров и предсказание предметной области |
| Файл документа-основания | PDF, DOCX и иные | прикрепление оригинала с контрольной суммой SHA-256 |
| Граф регламента | JSON: `rule_id`, `regulation_id`, `nodes`, `edges` | программа на языке Flow DSL |
| Измерения для прогона | JSON, список объектов с полем `value` и одним из: `sensor_id`, `param_id`, `sensor_type`; необязательно `external_id`, `edge_id` — они на логику не влияют и переносятся в трассу | входные значения регламента |

| События внешних систем | JSON через шлюз событий | боевое исполнение по расписанию или по приёму |

### 4.2. Выходные данные

**Результат прогона** (`backend/app/services/flow_executor.py:102`):

| Поле | Содержание |
|---|---|
| `level` | уровень критичности: 0 — норма, иначе максимум `priority` сработавших выходов |
| `regulation_id`, `regulation_name` | регламент, выдавший вердикт |
| `recommendation` | тексты сработавших выходов |
| `fired_nodes`, `fired_edges` | сработавшие узлы и связи — подсветка на схеме |
| `trace` | трасса вердикта: по каждому пройденному узлу — тип, признак срабатывания, значение и пояснение на русском языке |
| `inputs_resolved`, `incident_id` | какие значения фактически попали во входы; идентификатор записи в журнале прогонов |

**Прочие выходные данные:** предупреждения проверки при сохранении графа (поле `lint`) и сводки синхронизации параметров и триггеров; отчёт проверки регламента с тремя корзинами, сводной фразой и счётчиками; семантическое представление в Turtle и форма ограничений SHACL; обменный комплект регламента или двойника процесса в виде архива; записи журнала прогонов; выгрузки в CSV. Примеры пояснений в трассе: «20.5 в норме [19.0, 22.0] атм»; «25.0 вне [19.0, 22.0] → out_of_range»; «switch: routed by case bounds → ['critical']»; «уровень 2: Эскалация инвестору…».

## Приложение А. Сквозной пример: контроль срока этапа строительного проекта

Пример построен на регламенте `construction-overdue-stage`, входящем в поставку (`backend/data/fixtures/construction-overdue-stage.data.ttl`, `.flow.json`, `.shapes.ttl`).

### А.1. Исходная норма

Основание — договор строительного подряда (ГК РФ, глава 37); сроки и неустойка — статьи 708 и 330 ГК РФ. Содержательное правило: при просрочке этапа подрядчик несёт ответственность; при критическом отставании вопрос выносится инвестору вплоть до расторжения договора. Крупный договор эскалируется быстрее.

### А.2. Извлечение параметров

Текст нормы вводится в разделе «Создать из текста». Из него отбираются шесть параметров:

| Параметр | Смысл | Эталон | Границы |
|---|---|---|---|
| `overdueDays` | измеренная просрочка этапа, дней | 0.0 | ≥ 0 |
| `contractValueMillionRub` | сумма договора, млн ₽ | 85.0 | ≥ 0 |
| `allowedOverdueDays` | допустимая просрочка (настройка) | 3.0 | — |
| `criticalOverdueDays` | критическая просрочка (настройка) | 14.0 | — |
| `penaltyRubPerDay` | неустойка за день (настройка) | 50000.0 | — |
| `reviewWindowDays` | окно на пересмотр графика (настройка) | 5.0 | — |

Первые два параметра — измеряемые, остальные — настраиваемые пороги и политика. Нижние границы двух измеряемых параметров переносятся в форму ограничений: `sh:minInclusive 0.0`, `sh:minCount 1` (файл `.shapes.ttl`).

### А.3. Сборка графа

Восемь узлов и восемь связей:

| Узел | Тип | Настройка |
|---|---|---|
| `n_sensor_overdue` | Событие | подтип `pms-stage-overdue`, поле `overdue_days`, привязка к `n_in_overdue` |
| `n_sensor_contract` | Событие | подтип `pms-contract-meta`, поле `contract_value_million_rub`, привязка к `n_in_contract` |
| `n_in_overdue` | Вход | `paramRef = overdueDays` |
| `n_in_contract` | Вход | `paramRef = contractValueMillionRub` |
| `n_formula` | Формула | `overdueDays * (1 + contractValueMillionRub / 200)` |
| `n_switch` | Развилка | зоны: «В графике» `ok` `max = 3`; «Просрочка» `overdue` `min = 3`, `max = 14`; «Критическая просрочка» `critical` `min = 14` |
| `n_out_ok` | Выход | действие `monitor_only`, приоритет 0 |
| `n_out_gip` | Выход | действие `notify_gip_with_penalty`, приоритет 1 |
| `n_out_investor` | Выход | действие `escalate_investor`, приоритет 2 |

Связи: оба узла «Событие» — к своим входам; оба входа — к формуле; формула — к развилке; развилка — к трём выходам с ключами `ok`, `overdue`, `critical`.

Формула превращает две величины в одно число «риск-дни»: договор на 85 млн ₽ даёт множитель `1 + 85 / 200 = 1.425`. Тем самым один и тот же календарный срыв на крупном договоре быстрее доходит до эскалации.

### А.4. Проверка правила

Сохранение графа возвращает три предупреждения `output_unknown_action`: коды действий `monitor_only`, `notify_gip_with_penalty`, `escalate_investor` являются доменными и отсутствуют в реестре обозначений (приложение Б), поэтому платформа предупреждает о возможной опечатке. Сохранение при этом выполняется. Действие аналитика — либо привести коды к реестровым (`no_action`, `notify_gip`, `escalate_to_investor`), либо сознательно оставить доменные: на порядок исполнения это не влияет, поскольку предписанное действие в любом случае выполняет человек по тексту вердикта (приложение Б).

Вкладка «Проверка регламента» противоречий и пробелов не показывает: зоны развилки состыкованы встык и покрывают всю числовую ось; выход `notify_gip_with_penalty` распознаётся как ветвь оповещения, что снимает риск молчаливого не-вердикта при нехватке данных; выходы «одобрить» и «заблокировать» разведены развилкой.

### А.5. Прогон на тестовых данных

Запрос: `POST /api/regulations/construction-overdue-stage/execute` с измерениями `{sensor_id: "n_sensor_overdue", value: 10}` и `{sensor_id: "n_sensor_contract", value: 85}`.

| Просрочка, дней | Сумма договора, млн ₽ | Риск-дни | Зона | Сработавший выход | Уровень |
|---|---|---|---|---|---|
| 2 | 85 | 2.85 | `ok` | «В графике» | 0 |
| 5 | 85 | 7.125 | `overdue` | «ГИП + штраф» | 1 |
| 10 | 85 | 14.25 | `critical` | «Эскалация инвестору» | 2 |

Трасса третьего прогона по шагам: два узла «Событие» сработали со значениями 10 и 85; два входа приняли значения; формула вычислила `10 * (1 + 85 / 200) → 14.25`; развилка выдала «switch: routed by case bounds → ['critical']»; выход выдал «уровень 2: Критическая просрочка (с учётом масштаба договора). → Эскалация инвестору, рассмотрение санкций и расторжения договора». Граничный случай: при риск-днях ровно 14.0 срабатывает зона `critical`, поскольку нижняя граница зоны включается, а верхняя — нет.

### А.6. Критерий решённости и публикация

Для домена «construction» по умолчанию предлагается критерий `no_violation` — регламент считается исполненным, если уровень вердикта равен нулю. Для настоящего регламента содержательно точнее `specific_output` с ожидаемым выходом `monitor_only`: этап вернулся в график. При выборе вида `task_closed_within_sla` обязательно задаётся срок в секундах, иначе проверка критерия выдаст `PRIMARY_INVALID_SLA`; при этом следует помнить, что задача заводится из карточки вердикта вручную (приложение Б).

После проверки регламент публикуется переводом в статус «активный». С этого момента он исполняется автоматически по данным, поступающим из системы управления строительными проектами Plan-R, а результаты видны в разделах «Стройка · Plan-R» и «Журнал прогонов».

### А.7. Семантическое представление

Регламент в Turtle содержит экземпляр `:ConstructionOverdueStageRegulation` класса `:Regulation` с плоскими свойствами параметров, наименованием, датой, текстом рекомендации, ссылкой на документ-основание (`:sourceDocument`) и пункт (`:sourceClause`); форма ограничений содержит `:RegulationShape` с обязательностью и нижними границами двух измеряемых параметров. Оба файла выгружаются в обменном комплекте регламента.

## Приложение Б. Реестр кодов действий выходного узла

Реестр задан в `backend/app/services/flow_validators.py:48`. Реестр — это **словарь допустимых обозначений действия**, а не перечень кодов, за которыми закреплён автоматический обработчик. Назначение реестра — единообразие обозначений и подсказка при опечатке. Код вне реестра сохранить можно, но он сопровождается предупреждением `output_unknown_action`.

**Предупреждение аналитику (методологу) — существенно.** Из принадлежности кода реестру **не следует**, что по нему выполнится автоматическое действие. Ни за одним реестровым кодом на дату выпуска настоящего руководства не закреплён автоматический исполнитель: код действия — машиночитаемое обозначение предписания, которое выполняет человек по тексту вердикта. Внутри изделия код действия используется в двух местах и только для рассуждения о правиле: при сверке критерия `specific_output` (`backend/app/services/etl/applier.py:68`) и при анализе взаимоисключающих выходов (`CONTRADICTORY_OUTPUTS`, см. ниже).

Частный случай, о котором следует знать особо, — `create_leyka_task` (заведение задачи в трекере). В коде исполнителя предусмотрена ветка автоматического заведения задачи, но она ищет код действия `leyka_create_task` (`backend/app/services/etl/applier.py:699`), тогда как реестр действий и все поставляемые регламенты используют обратный порядок слов — `create_leyka_task` (`backend/app/services/flow_validators.py:53`). Обозначения не совпадают, поэтому **ни один поставляемый регламент задачу не заводит**, и код `create_leyka_task`, будучи реестровым, автоматического обработчика не имеет. Задача заводится человеком из карточки вердикта в разделе «Исполнение». Автоматическое заведение задачи по срабатыванию регламента для поставляемых регламентов отнесено к развитию платформы (приложение А ТЗ 8.0, п. А.7).

Практическое следствие для аналитика: критерий решённости `task_closed_within_sla` (раздел 2.7) считает срок по задаче, заведённой вручную; ожидать, что задача появится сама по срабатыванию правила, нельзя.
