## 2. Функциональное назначение

### 2.1. Классы решаемых задач

Настройка добавляет к задачам ядра четыре отраслевые.

1. **Чтение состояния строительного портфеля из внешней системы управления проектами.** Читаются стройобъекты, графики, их актуальные версии, элементы структуры работ и договорные реквизиты (`backend/app/services/etl/planr_client.py:405`).
2. **Выявление рисков портфеля до наступления нарушения.** Четыре детектора над снимком портфеля дают ранжированный перечень тревог с предписанным действием и ролью адресата (`backend/app/services/planr_proactive.py:39`).
3. **Настраиваемая доставка вердикта ответственному лицу** по тройке «пространство → регламент → канал» без программирования (`backend/app/services/planr_bindings_store.py:74`).
4. **Исполнение пяти строительных регламентов** ядром на данных от видеодетекторов, весов на пропускном пункте, системы учёта поставок, распределённого акустического датчика и внешней системы управления проектами.

### 2.2. Границы применения

Границы объявлены в самом изделии — во встроенном руководстве монитора руководителя, и повторены здесь, потому что при приёмке о них спрашивают в первую очередь.

- **Связь односторонняя.** В рабочем контуре платформа только читает внешнюю систему и ничего в неё не записывает; единственный пишущий код — сидер демонстрационных объектов, вызываемый вручную.
- **Цепочки срыва по сети работ нет.** Просрочка этапа не распространяется по связям на зависимые работы: платформа показывает состояние, а не пересчитывает график.
- **Просрочка отсчитывается от графика.** Устаревший график даёт недостоверную оценку — на это указывает отдельный детектор.
- **Контакты берутся из собственного справочника,** поскольку внешняя система не отдаёт их программным интерфейсом (см. 6.4).

## 3. Описание логической структуры

Раздел составлен по п. 2.4 ГОСТ 19.402-78: структура отраслевой части, алгоритмы, организация данных и связи с другими программами. Алгоритм исполнения регламента принадлежит ядру и изложен в 00000-00000-13, п. 3.3.

### 3.1. Клиент внешней системы управления строительными проектами

**Модель данных, на которую настроен клиент:** пространство → группа объектов → стройобъект → график → версия графика → элемент структуры работ (`backend/app/services/etl/planr_client.py:13`).

**Точки внешнего интерфейса.** Ко всем путям добавляется префикс `/public-api` (`planr_client.py:179`).

| Точка | Что читается |
|---|---|
| `GET /eps` | дерево объектов; отбираются узлы типов «стройобъект», «график», «группа», «пространство» |
| `GET /versions` | версии графиков; в обработку берутся со статусом «актуальная» и «версия» |
| `GET /wbs?EpsId=<версия>` | элементы структуры работ выбранной версии |
| `GET /eps-attributes` | словарь определений атрибутов договора |
| `GET /eps-attribute-values` | значения атрибутов; соединяются с объектами на стороне платформы |
| `GET /spaces?$top=1` | лёгкая проба доступности для контроля состояния |

Смысл системных атрибутов элемента структуры работ задан таблицей из 11 позиций: код, наименование, старт, финиш, процент выполнения, исполнитель, плановая и фактическая стоимость, целевой финиш, отклонение по срокам, статус (`planr_client.py:55`).

Сопоставление наименований атрибутов договора с каноническими ключами выполняется по подстроке наименования (10 правил), а для пространств без словаря определений — по восьми стабильным идентификаторам (`planr_client.py:281`).

**Авторизация.** Два заголовка: маркер доступа и идентификатор пространства (`planr_client.py:163`). Значение заголовка авторизации формируется по одной из трёх схем — «голый» маркер, `apikey` или `bearer` (`backend/app/config.py:217`); по умолчанию применяется первая. Основание выбора зафиксировано в коде: боевой экземпляр отвечал отказом 401 на форму `apikey` и успехом на «голый» маркер, вопреки руководству релиза (`backend/app/config.py:125`). Если маркер уже содержит префикс схемы, повторно он не добавляется (`config.py:229`). Маркер объявлен несериализуемым в представление, чтобы не попадать в машиночитаемую схему и журналы (`config.py:137`).

**Встроенный имитатор.** При незаданном адресе внешней системы обращения направляются на имитатор в том же процессе (`backend/app/api/_planr_mock.py`), смонтированный без включения в машиночитаемую схему (`backend/app/main.py:381`). Признак боевого режима — непустой адрес, не указывающий на локальный узел.

### 3.2. Детекторы риска строительного портфеля

Четыре детектора, реализованные **чистой детерминированной функцией** над готовым снимком портфеля; языковая модель в вычислении не участвует, все пороги заданы в коде (`backend/app/services/planr_proactive.py:39`).

| Детектор | Что находит | Порог | Уровень | Адресат |
|---|---|---|---|---|
| Смещение критического пути | просрочка этапов на критическом пути | 14 дней и более | критично, иначе внимание | главный инженер проекта |
| Перерасход бюджета | превышение факта над планом по стоимости | **порога нет** — любое превышение при ненулевом плане | внимание, независимо от величины | сметчик |
| Приближающийся срок | плановый финиш близко при недостаточной готовности | 7 дней и менее при готовности ниже 90 % | упреждающий | — |
| Устаревший график | график давно не пересчитывали | 60 дней | сведение | планировщик |

Существенные особенности реализации:

- Число затронутых этапов берётся из **полного счётчика сводки**, а не из усечённого показываемого среза: на больших портфелях счёт не занижается.
- Детектор устаревшего графика фиксирует **не нарушение, а искажение картины**: оценка просрочек и прогноз по непересчитанному графику недостоверны.
- Тревоги ранжируются по двум ключам: серьёзность, затем число затронутых объектов по убыванию.
- При отсутствии данных детекторы возвращают пустой перечень — риски не домысливаются.

### 3.3. Привязки доставки вердикта

Модель — тройка «пространство → регламент → канал доставки», хранится таблицей из десяти столбцов в той же базе, что и оперативные данные ядра (`backend/app/services/planr_bindings_store.py:74`). Обязательные поля — пространство и регламент; объект необязателен. Значения по умолчанию: канал «автоматически», получатель пуст, привязка включена.

**Автопосев.** Для пространства без привязок идемпотентно заводятся две привязки — контроль сроков этапа и портфельный риск. Остальные три регламента администратор привязывает вручную.

**Подавление повторов.** Вторая таблица хранит по каждому пространству множество ключей уже отправленных критических событий. Ключ — объединение пар «объект, этап» для этапов с просрочкой от 14 дней и троек «регламент детектора, число затронутых объектов». Автоматическая рассылка выполняется **только при ухудшении**: если новых ключей нет, отправка не производится. Состояние сохраняется всегда, поэтому ушедший и вновь появившийся риск уведомляет заново.

**Разрешение получателя** трёхступенчатое: по фамилии, затем по роли, затем адресат по умолчанию из конфигурации. Канал «автоматически» разрешается в Telegram при наличии его маркера, иначе в MAX.

### 3.4. Регламенты строительной области

Пять регламентов, каждый — тройка файлов (граф решения, данные и параметры, ограничения). Все пять построены **по одной топологии**: два узла-датчика, два узла-входа, узел-формула, узел-переключатель, три узла-выхода — девять узлов и восемь рёбер. Иных типов узлов не применяется.

Устройство одинаково: два измеряемых входа сворачиваются формулой в один показатель, переключатель по двум границам даёт три вердикта, каждому вердикту соответствует своё предписанное действие. Пороги вынесены в настраиваемые свойства онтологии, а не зашиты в граф.

Подробно — приложение А.

### 3.5. Связи с другими программами

Связи ядра (мессенджеры, система управления задачами, языковая модель) описаны в 00000-00000-13, п. 3.5. Настройка добавляет одну связь — с внешней системой управления строительными проектами (п. 3.1) и одно применение существующих: доставку отраслевого дайджеста в мессенджер по привязкам (п. 3.3).

## 5. Вызов и загрузка

Собственной точки входа у настройки нет: она загружается вместе с ядром. Порядок вызова и загрузки — 00000-00000-13, раздел 5.

**Настройка отраслевой части** выполняется переменными окружения (11710-11710-12, раздел 4). Существенные для порядка работы:

| Переменная | Умолчание | Действие |
|---|---|---|
| `PLANR_BASE_URL` | пусто | пустое значение замыкает обращения на встроенный имитатор |
| `PLANR_AUTH_TOKEN` | `demo-token-2026` | **пустое значение полностью отключает интеграцию** |
| `PLANR_AUTONOTIFY` | включено | автоматическая доставка дайджеста при ухудшении |

**Периодичность.** Опрос внешней системы выполняет планировщик ядра по источнику `planr-pms` с интервалом по умолчанию 300 секунд и только при включённом источнике. Прогон детекторов встроен в сборку снимка портфеля и выполняется при каждом опросе.

**Изоляция отказов.** Сбой автоматической доставки не прерывает опрос: обработчик обёрнут в перехват исключений. Доставка выполняется по каждому пространству отдельно, и отказ одного не прерывает обработку остальных.

## 6. Входные данные

### 6.1. Данные внешней системы управления проектами

Состав — п. 3.1. Опрос по инициативе платформы, только чтение, формат обмена — JSON.

### 6.2. Показания источников событий

| Источник | Подтип | Что даёт | Какой регламент потребляет |
|---|---|---|---|
| Видеодетектор средств защиты | `vd-ppe-helmet`, `vd-ppe-safety-vest` | число нарушений за смену | контроль применения средств защиты |

Реестр подтипов датчиков прямо указывает, какой строительный регламент потребляет каждый подтип.

### 6.3. Регламенты и датасеты как входные данные настройки

Пять регламентов (15 файлов) и шесть датасетов графа знаний строительной области — **859 триплетов**: онтология строительной безопасности, роли и профессии (438 триплетов — самый крупный), городское капитальное строительство, оптоволоконный мониторинг, каталог видеодетекторов (180).

### 6.4. Справочник контактов

Ведётся файлом `backend/data/fixtures/planr-contacts.json` с двумя разделами — по фамилии и по роли. Собственный справочник понадобился потому, что **внешняя система не отдаёт контакты программным интерфейсом**: у объекта есть только фамилия в атрибутах, без почты и телефона.

Отсутствие файла трактуется как пустой справочник, повреждённый — как пустой с записью предупреждения; отказа не происходит. **Поставляемый справочник пуст** — следствие см. в приложении Б.

## 7. Выходные данные

### 7.1. Тревоги детекторов

Каждая тревога — запись из девяти полей: идентификатор регламента, серьёзность, значок, заголовок, пояснение, предписанное действие, роль адресата, счётчик затронутых объектов и до пяти конкретных примеров.

### 7.2. Вердикты регламентов

Формат вердикта, трасса вычисления и запись в журнал прогонов принадлежат ядру (00000-00000-13, раздел 7). Отраслевые предписанные действия перечислены в приложении А.

### 7.3. Дайджест в мессенджер

Компактная сводка тревог — не более шести строк-заголовков с предписанным действием под каждой. Строится на кешированном снимке портфеля: тяжёлый опрос внешней системы при отправке не выполняется, а при отсутствии кеша отправка не производится и возвращается причина.

При незаданном маркере бота отправка переходит в «сухой» режим — запись в журнал без сетевого обращения.

### 7.4. Экраны платформы

Настройка добавляет два раздела интерфейса — «Стройка · Plan-R» (маршрут `/planr`) и «Контуры интеграции» (`/planr-bindings`) — и посадочную страницу платформы (`/archi`). Оба раздела загружаются отложенно.

**Монитор руководителя** построен из пяти блоков в фиксированном порядке чтения: тревоги «Требует решения», живой портфельный вердикт, восемь показателей портфеля, перечень объектов, свёрнутые разборы. Снимок перечитывается раз в 60 секунд. В шапке выводится индикатор режима источника — боевой или встроенный контур. Экран прямо отделяет боевые объекты от демонстрационных.

**Ролевая видимость.** Раздел «Стройка · Plan-R» по умолчанию виден четырём ролям из пяти (аналитику-методологу — нет), «Контуры интеграции» — трём. Настройка вводит пятую роль «Строитель» с домашним маршрутом `/planr`. Видимость не зашита жёстко: администратор переопределяет набор ролей для любого раздела.

| Регламент | Что контролирует | Входы | Свёртка | Границы | Вердикты и действия |
|---|---|---|---|---|---|
| Средства защиты (`construction-ppe-violation`) | применение каски и сигнального жилета на площадке | нарушений без каски и без жилета за смену | сумма | 2 и 5 | в норме → только мониторинг; превышен лимит → задача прорабу и сообщение; критично → эскалация инженеру по охране труда |

| Охрана оптоволокна (`construction-fiber-cable-protection`) | несанкционированная копка и присутствие людей у подземного кабеля | число критичных и предупредительных событий датчика | индекс угрозы: критичные × 100 + предупредительные — одно критичное перевешивает любое число предупредительных | 1 и 100 | под наблюдением; предупреждение → выезд патруля на координату вдоль волокна; критично → врезка либо повреждение |

**Документы-основания**, указанные в самих данных регламентов:

| Регламент | Основание |
|---|---|
| Средства защиты | Приказ Минтруда России № 883н «Правила по охране труда при строительстве, реконструкции и ремонте» |
| Сроки этапа | договор строительного подряда, ГК РФ глава 37, ст. 708 и 330 |
| Входной контроль | ФЗ № 384-ФЗ «Технический регламент о безопасности зданий и сооружений»; ГОСТ 24297-2013 |

## ПРИЛОЖЕНИЕ Б. Расхождения, выявленные при составлении

Правка не выполнена; приложение — перечень найденного.

**1. Логика регламента продублирована в интерфейсе.** Портфельный вердикт и вердикт по отдельному этапу **вычисляются на клиенте** по показателям снимка, а не берутся от интерпретатора: на клиенте заново заданы границы 14 и 7 дней и соответствующие исходы. Это расходится с основным принципом изделия — решение принимает интерпретатор регламента, а интерфейс его отображает. Практическое следствие: правка порогов в регламенте не изменит того, что показано на экране монитора.

**2. Датасет продублирован побайтово.** `construction/construction_safety.ttl` и `construction/construction-safety-ontology.ttl` содержат по 69 триплетов и различаются единственной строкой заголовка с именем файла. Один из двух подлежит удалению.

**3. Критерий решённости не задан ни у одного из пяти регламентов машиночитаемым полем.** Словесно он приведён в тексте рекомендации у трёх из пяти; машинный критерий назначается платформой по домену — четырём регламентам домена «строительство» присваивается критерий вида «нет нарушений», регламенту охраны оптоволокна — «сработала ожидаемая ветвь эскалации». Персональных переопределений нет.

**4. Поставляемый справочник контактов пуст**: оба раздела не заполнены. Следствие — все вердикты уходят адресату по умолчанию, а трёхступенчатое разрешение получателя (по фамилии, по роли, по умолчанию) на поставляемом наполнении вырождается в третью ступень.

**5. Приоритеты выходов регламента охраны оптоволокна — 0, 1 и 3**, значение 2 пропущено, тогда как у остальных четырёх регламентов приоритеты 0, 1, 2. Расхождение не влияет на работу, но нарушает единообразие.

**6. Автопосевом привязываются два регламента из пяти.** Три остальных — контроль средств защиты, входной контроль, охрана оптоволокна — к контурам доставки автоматически не привязываются и требуют ручной настройки администратором. Экран монитора это оговаривает, но при первом развёртывании поведение неочевидно.

**7. У детектора перерасхода бюджета отсутствует порог допустимого превышения.** Тревога формируется при любом превышении факта над планом, уровень фиксирован как «внимание» независимо от величины. На портфеле с обычным колебанием стоимости это даст постоянную тревогу.

**8. Карточек стройобъектов в Ситуационном центре нет.** Ни один компонент раздела не обращается к внешней системе управления строительными проектами; вкладка «Оптоволокно (DAS)» относится к настройке по содержанию регламента, а не по источнику данных платформы.
