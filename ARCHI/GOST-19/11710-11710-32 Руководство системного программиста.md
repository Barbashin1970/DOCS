## 1. Общие сведения о программе

### 1.1. Назначение программы

Платформа АРХИ обеспечивает информационную поддержку принятия решений при управлении строительными проектами: принимает события внешних систем и датчиков, исполняет на них цифровые двойники регламентов (ЦДР), формирует вердикт с трассой вычисления и доставляет вердикт ответственному в мессенджер.

Поручение исполнителю заводится в трекере задач **вручную — из карточки вердикта**. Автоматическое заведение задачи по срабатыванию регламента отнесено к приложению А.7 технического задания и не реализовано.

Платформа реализована на программной платформе РАГРАФ и представляет собой единое серверное приложение с веб-интерфейсом.

### 1.2. Функции, выполняемые программой

| Функция | Подсистема |
|---|---|
| Приём событий по HTTP и опрос внешних источников по расписанию | шлюз событий |
| Детерминированное исполнение регламента, записанного на языке Flow DSL | ядро исполнения |
| Хранение регламентов, версий, документов-оснований, журнала прогонов | хранилище цифровых активов |
| Чтение данных системы управления строительными проектами Plan-R | интеграционный слой |
| Доставка вердиктов в каналы Telegram и MAX; создание задач в трекере по команде оператора из карточки вердикта | интеграционный слой |
| Веб-интерфейс аналитика, оператора, инженера, руководителя, строителя | клиентская часть |

### 1.3. Программные и технические средства

| Компонент | Значение |
|---|---|
| Операционная система сервера | Linux (проверено на образе `python:3.12-slim`) |
| Язык и среда исполнения серверной части | Python 3.12 |
| Каркас серверной части | FastAPI 0.115.4, сервер приложений uvicorn 0.32.0 |
| Хранилище | DuckDB (пакет `duckdb>=1.2,<2`), файл на дисковом томе |
| Работа с семантическими форматами | rdflib 7.1.1, pyshacl 0.26.0 |
| Клиентская часть | React 18, TypeScript, сборщик Vite, Node.js 20 (только на этапе сборки) |
| Оперативная память | минимально 2 ГБ, рекомендуется 4 ГБ (техническое задание, п. 4.4) |
| Дисковое пространство | том не менее 1 ГБ на данные; фактический расход на пилоте — около 3 МБ, прогноз на 6 месяцев эксплуатации — 25–40 МБ |
| Число рабочих процессов | один (`--workers 1`); хранилище DuckDB не рассчитано на многопроцессный доступ |

Прогноз расхода дискового пространства складывается из трёх составляющих: файл хранилища с журналом предзаписи — 15–30 МБ, каталог снимков версий `versions/` — около 5 МБ, каталог графов исполнения `flows/` — около 5 МБ. Итого 25–40 МБ за шесть месяцев эксплуатации; та же оценка приведена в документе 11710-11710-31 «Описание применения», п. 2.3. Оценка относится к эксплуатации с типовой интенсивностью правок: на стенде разработки, где снимок версии создаётся на каждое изменение регламента, каталог `versions/` растёт значительно быстрее, и его следует контролировать отдельно. Вложенные документы-основания в оценку не входят и учитываются отдельно: предел одного файла — 25 МБ (`backend/app/services/source_documents.py:29`).

Полный перечень зависимостей серверной части — `backend/requirements.txt`. Дополнительные системные пакеты не устанавливаются: HTTPS-сертификаты поставляются пакетом `certifi` в составе `httpx`.

## 2. Структура программы

### 2.1. Общее строение

Программа собирается в один контейнер: собранная клиентская часть размещается рядом с серверной, и один процесс uvicorn отдаёт и программный интерфейс, и веб-интерфейс. Отдельный веб-сервер и отдельный процесс Node.js не требуются (`backend/app/main.py:391`).

```
HTTPS → uvicorn (один процесс, порт PORT)
          ├ /api/*      — 234 обработчика запросов программного интерфейса
          ├ /api/health — контроль живости
          ├ /docs       — документация интерфейса
          ├ /assets/*   — статика клиентской части
          └ /*          — index.html (маршруты клиента)
                 │
       каталог данных DATA_DIR
          ├ regulations.duckdb (+ .wal) — хранилище
          ├ flows/     — графы исполнения
          ├ versions/  — снимки версий
          └ source_documents/ — документы-основания
```

### 2.2. Состав серверной части

Каталог `backend/app`:

| Каталог, файл | Назначение |
|---|---|
| `main.py` | точка входа: сборка приложения, подключение маршрутизаторов, жизненный цикл, раздача клиентской части |
| `config.py` | все настраиваемые параметры (см. раздел 3) |
| `auth.py` | административный вход, проверка прав на изменение данных |
| `api/` | 30 маршрутизаторов программного интерфейса, 234 обработчика запросов |
| `services/` | прикладная логика: ядро исполнения, хранилища, интеграции, анализ |
| `services/etl/` | шлюз событий на опросе: планировщик, сборщики данных источников, применение регламентов, резолвер критерия решённости |
| `schemas/` | описания предметных сущностей и языка Flow DSL |
| `adapters/` | преобразование форматов внешних систем |

Ключевые модули: ядро исполнения — `services/flow_executor.py`; планировщик опроса — `services/etl/scheduler.py`; применение регламентов к данным — `services/etl/applier.py`; клиент Plan-R — `services/etl/planr_client.py`; хранилище регламентов — `services/regulation_store.py`; хранилище оперативных данных и состояния каналов — `services/live_data_store.py`.

### 2.3. Подключение маршрутизаторов

Маршрутизаторы подключаются в `backend/app/main.py:345` и далее, все с префиксом `/api`. Порядок значим: перехватывающий маршрут клиентской части регистрируется **после** всех программных, иначе он перехватил бы `/api/*` (`backend/app/main.py:406`).

Отдельно подключается внутренняя эмуляция сервера Plan-R (`backend/app/main.py:381`) — она не входит в публичную схему и используется только когда боевой адрес Plan-R не задан.

### 2.4. Жизненный цикл приложения

Обработчик жизненного цикла — `backend/app/main.py:18`. При запуске последовательно выполняются шаги, каждый в отдельном блоке перехвата ошибок, поэтому сбой одного шага не препятствует запуску:

1. Создание схемы хранилища и первичное заполнение из фикстур — `regulation_store.init_db()`.
2. Создание реестра полей датчиков — `sensor_schema_store.init_db()`.
3. Создание словаря терминов извлечения — `extraction_term_store.init_db()`.
4. Загрузка демонстрационных документов, если их нет.
5. Загрузка проверочных вопросов по регламентам, если их нет.
6. Создание схемы оперативных данных и настроек пульта источников; запуск фонового планировщика опроса, если он не выключен (`backend/app/main.py:68`).
7. Запуск опроса статусов задач трекера, если заданы учётные данные бота (`backend/app/main.py:76`).

При остановке штатно снимаются фоновые задачи, после чего выполняется принудительный сброс журнала предзаписи хранилища командой `CHECKPOINT` (`backend/app/main.py:107`). Этот шаг обязателен: без него следующий запуск может не открыть файл хранилища (см. п. 6.4).

### 2.5. Состав клиентской части

Каталог `frontend/src`: `components/` — экраны по разделам интерфейса, `lib/` — обращения к программному интерфейсу и общие правила, `store/` — состояние редактора графа. Перечень разделов и их видимость по ролям задаётся в `frontend/src/lib/navSections.ts`, перечень ролей — в `frontend/src/lib/roles.ts`.

Сборка клиентской части (`npm run build`) помещается в каталог, указанный параметром `STATIC_DIR`.

### 3.3. Настройка подключения к Plan-R

Клиент передаёт **два** заголовка (`backend/app/services/etl/planr_client.py:163`):

- `Authorization` — значение формируется по схеме `PLANR_AUTH_SCHEME` (`backend/app/config.py:197`);
- `x-tenant-id` — значение `PLANR_TENANT_ID`, идентификатор пространства из административной консоли Plan-R.

Схема по умолчанию — `raw`, то есть заголовок содержит **голый токен без префикса**. Проверкой установлено, что боевой экземпляр отвечает кодом 200 на голый токен и кодом 401 на форму `apikey <токен>`, несмотря на указания руководства по эксплуатации Plan-R. Значение `apikey` следует задавать только если конкретный экземпляр требует именно его. Если токен уже содержит префикс `apikey ` или `bearer `, он передаётся без изменений.

Порядок настройки:

1. Получить токен и идентификатор пространства в административной консоли Plan-R.
2. Задать `PLANR_BASE_URL`, `PLANR_AUTH_TOKEN`, `PLANR_TENANT_ID`, при необходимости `PLANR_SPACES`.
3. Перезапустить приложение.
4. Открыть `GET /api/live/planr/health` (`backend/app/api/live.py:75`) и убедиться, что в ответе `mode: "live"` и `reachable: true`. Токен в ответе не раскрывается — возвращается только схема авторизации.

Обмен с Plan-R выполняется **только на чтение**. Обратная запись в систему управления проектами не реализована (приложение А.1 технического задания).

Интеграция с иными системами управления проектами (Oracle Primavera, Microsoft Project, Redmine, 1С) и с системами электронного документооборота не реализована (приложение А.1 технического задания).

### 3.4. Настройка каналов доставки

Оба канала работают по одинаковой схеме: при пустом токене система переходит в «сухой» режим — сообщение формируется и записывается в журнал, но не отправляется.

Порядок для Telegram:

1. Получить токен бота, задать `TELEGRAM_BOT_TOKEN`, перезапустить приложение.
2. Написать боту или добавить его в группу.
3. Открыть `GET /api/live/telegram/updates` (`backend/app/api/live.py:213`) и взять из ответа идентификатор чата.
4. Задать `TELEGRAM_DEFAULT_RECIPIENT`, перезапустить приложение.
5. Проверить канал: `POST /api/live/telegram/test` (`backend/app/api/live.py:205`); состояние — `GET /api/live/telegram/health` (`backend/app/api/live.py:193`).

Порядок для MAX аналогичен: `MAX_BOT_TOKEN`, `GET /api/live/max/updates` (`backend/app/api/live.py:183`), `MAX_DEFAULT_RECIPIENT`, `POST /api/live/max/test` (`backend/app/api/live.py:175`), `GET /api/live/max/health` (`backend/app/api/live.py:163`). Получатель задаётся в форме `user:<id>` для личной переписки или `chat:<id>` для группового чата, в котором состоит бот.

Адресная доставка настраивается без изменения параметров — в разделе интерфейса «Контуры интеграции» привязками «пространство — регламент — канал — получатель».

Подсистемой рассылки обрабатываются **только два канала — Telegram и MAX** (`backend/app/api/live.py:253`). Значение «LEYKA (задача)», доступное в списке каналов интерфейса, не обрабатывается: привязка с этим каналом молча уходит в Telegram. Задавать его не следует; задача в трекере заводится вручную из карточки вердикта (см. п. 1.1).

Приём входящих сообщений мессенджера не реализован (приложение А.3 технического задания).

### 3.5. Административный пароль

Разграничение доступа на изменение обеспечивает единый административный пароль `ADMIN_PASS` (`backend/app/auth.py:91`):

- пароль не задан — защита выключена, изменение и удаление доступны любому посетителю; допустимо только для стенда разработки;
- пароль задан — защищённые операции требуют куки `ragraf_admin`, выдаваемой методом `POST /api/auth/admin/login` (`backend/app/auth.py:186`).

Куки не хранится на сервере: это значение с кодом подлинности HMAC-SHA256 на ключе `ADMIN_PASS`, поэтому сеанс переживает перезапуск приложения. Куки закрыта от чтения сценариями браузера, ограничена по источнику и на защищённом соединении выставляется с признаком передачи только по HTTPS. Пароль сравнивается в постоянном времени.

Смена пароля выполняется изменением `ADMIN_PASS` и перезапуском; все ранее выданные сеансы при этом становятся недействительными.

Реестр пользователей, права по проектам и двухфакторная аутентификация не реализованы (приложение А.6 технического задания). Доступ на запись — один административный пароль.

### 3.6. Токен приёма событий

Приём внешних событий по HTTP защищён общим секретом `INGEST_TOKEN`, передаваемым отправителем в заголовке `X-Ingest-Token`. Проверка выполняется в постоянном времени (`backend/app/api/ingest.py:142`). При пустом значении приём открыт — допустимо только на этапе наладки интеграции.

Предельный размер одной пачки событий различается по каналам приёма; при превышении возвращается код 413.

| Канал приёма | Предел пачки | Код |
|---|---|---|
| Приём событий распознавания номеров | 2000 событий | `backend/app/api/ingest.py:86` |
| Приём шумовых событий | 5000 событий | `backend/app/api/noise.py:33` |

### 3.7. Развёртывание

Основной способ — образ контейнера, собираемый по `Dockerfile` в корне репозитория (двухэтапная сборка: клиентская часть на Node.js 20, затем среда Python 3.12). Точка входа — `start.sh`: она передаёт права на каталог данных непривилегированному пользователю, проверяет целостность хранилища, при первом запуске заполняет том образцовыми данными и запускает uvicorn.

Порядок развёртывания на площадке Railway подробно изложен в `docs/DEPLOY.md`: корневой каталог сборки — `/`, том монтируется на `/data` размером 1 ГБ, путь контроля живости — `/api/health` с предельным временем 90 с (`railway.json`). Запасные площадки описаны в `docs/DEPLOY-FLY.md` (полноценный второй экземпляр) и `docs/DEPLOY-VERCEL.md` (только страница-визитка).

Локальный запуск для наладки: `./start.command` (macOS, Linux) или `start.bat` (Windows) — поднимает серверную часть на порту 8000 и клиентскую на порту 5173.

### 3.8. Локальная языковая модель

Диалоговый ассистент «Сима · Студия» может работать на языковой модели, установленной на той же машине. Обращений во внешнюю сеть при этом не происходит — режим предназначен для закрытого контура (п. 4.8 (5) технического задания), для приёмочных испытаний и для площадок, где передача данных внешнему поставщику недопустима.

Числовая часть изделия от языковой модели не зависит: все значения в вердиктах вычисляются кодом (п. 4.8 (3) технического задания). Модель формулирует текст ответа и участвует в диалоге.

#### 3.8.1. Состав

| Назначение | Модель | Объём | Обязательна |
|---|---|---|---|
| Диалог, формулировка ответа | `qwen2.5:7b-instruct-q4_K_M` | ≈ 4,7 ГБ | да |
| Векторные представления (смысловой поиск, разбор загруженных документов) | `bge-m3` | ≈ 1,2 ГБ | да |
| Облегчённая замена при нехватке памяти | `qwen2.5:3b-instruct-q4_K_M` | ≈ 2,0 ГБ | нет |

Среда исполнения — Ollama, свободно распространяемая, работает на macOS, Windows и Linux.

**Требования к машине:** 16 ГБ оперативной памяти и 8 ГБ свободного дискового пространства для основного состава. При 8 ГБ памяти применяется облегчённая модель: качество формулировок ниже, состав функций тот же.

Модель векторных представлений заменять не следует — от неё зависит смысловой поиск, и при смене модели ранее построенный индекс становится недействительным.

#### 3.8.2. Установка на macOS

**Шаг 1. Среда исполнения.** Один из двух способов:

```bash
brew install ollama
```

либо загрузить приложение с https://ollama.com/download/mac, распаковать и перенести в «Программы». Приложение при первом запуске само поднимает службу.

**Шаг 2. Запуск службы** (если ставили через `brew`):

```bash
ollama serve &
```

Служба слушает порт 11434. Проверка:

```bash
curl http://127.0.0.1:11434/api/tags
```

Ответ в виде `{"models":[...]}` означает, что служба работает.

**Шаг 3. Загрузка моделей.** Порядок важен: сначала языковая, она объёмнее.

```bash
ollama pull qwen2.5:7b-instruct-q4_K_M     # ≈ 4,7 ГБ
ollama pull bge-m3                          # ≈ 1,2 ГБ
```

Загрузка показывает ход в процентах. На канале 100 Мбит/с занимает около десяти минут, на медленном — дольше; прерванная загрузка возобновляется с того же места при повторном запуске команды.

**Шаг 4. Проверка состава:**

```bash
ollama list
```

Ожидаемый вывод содержит обе строки:

```
NAME                          ID              SIZE      MODIFIED
qwen2.5:7b-instruct-q4_K_M    845dbda0ea48    4.7 GB    ...
bge-m3:latest                 790764642607    1.2 GB    ...
```

Модели хранятся в `~/.ollama/models` и занимают около 5,4 ГБ. Каталог переопределяется переменной `OLLAMA_MODELS`.

#### 3.8.3. Установка на Windows

**Шаг 1. Среда исполнения.** Загрузить `OllamaSetup.exe` с https://ollama.com/download/windows и выполнить установку. Служба регистрируется автоматически, запускается при входе в систему и слушает порт 11434. Перезагрузка не требуется.

Проверка в командной строке:

```bat
curl http://127.0.0.1:11434/api/tags
```

Если команда `curl` не найдена (Windows 8 и старше), проверить можно в браузере по тому же адресу.

**Шаг 2. Загрузка моделей.** Открыть «Командную строку» либо PowerShell:

```bat
ollama pull qwen2.5:7b-instruct-q4_K_M
ollama pull bge-m3
```

**Шаг 3. Проверка состава:**

```bat
ollama list
```

**Куда сохраняются модели.** В профиль пользователя: `%USERPROFILE%\.ollama\models`, около 5,4 ГБ. Если системный диск мал, каталог переносится на другой том **до** загрузки моделей:

```bat
setx OLLAMA_MODELS "D:\ollama-models"
```

После `setx` закрыть и открыть окно командной строки заново, а службу Ollama перезапустить (значок в области уведомлений → выход, затем запуск из меню «Пуск») — иначе переменную она не увидит.

**Если в организации закрыт исходящий доступ.** Загрузка идёт с `registry.ollama.ai` по протоколу HTTPS. Требуется либо разрешить этот адрес, либо перенести модели с другой машины — порядок в 3.8.4.

#### 3.8.4. Перенос моделей на машину без доступа в сеть

Основной случай для закрытого контура: на рабочей машине интернета нет. Модели переносятся файлами, повторная загрузка не нужна.

**На машине с доступом в сеть** выполнить установку по 3.8.2 или 3.8.3 и скопировать каталог моделей целиком:

| Система | Что копировать |
|---|---|
| macOS, Linux | `~/.ollama/models` |
| Windows | `%USERPROFILE%\.ollama\models` |

Каталог содержит две части: `blobs` (сами веса, крупные файлы) и `manifests` (описания моделей, несколько килобайт). **Копировать нужно обе** — без `manifests` среда исполнения не увидит модели, хотя веса будут на месте.

Объём переноса — около 5,4 ГБ. Носитель: внешний диск, флеш-накопитель либо архив.

**На машине без доступа в сеть** установить саму среду исполнения (установщик переносится тем же способом), запустить её один раз, чтобы создался профиль, остановить и положить каталог `models` на то же место, заменив пустой. Затем проверить:

```
ollama list
```

Обе модели должны появиться в перечне. Загрузка при этом не выполняется — среда работает с локальными файлами.

**Проверка после переноса:** запустить изделие в локальном режиме (3.8.5) и задать контрольный вопрос из 3.8.6. Сетевое соединение при этом можно держать отключённым — это и подтвердит работу в закрытом контуре.

#### 3.8.5. Запуск изделия в этом режиме

Отдельная настройка не требуется — параметры выставляет сам скрипт запуска:

| Система | Действие |
|---|---|
| macOS, Linux | `./start.command`, пункт меню **5) Локальная модель**, либо `./start.command --local` |
| Windows | `start.bat`, пункт меню **5) Локальная модель**, либо `start.bat --local` |

Скрипт проверяет наличие Ollama, при необходимости запускает её, сверяет наличие моделей и **запрашивает согласие** перед загрузкой недостающих — объём измеряется гигабайтами, и решение принимает человек. Затем выставляет параметры подключения и поднимает изделие.

Настройки передаются переменными окружения, которые имеют приоритет над файлом `backend/.env`, поэтому рабочий файл площадки этот режим не изменяет и не перезаписывает.

#### 3.8.6. Проверка

После запуска открыть `/api/sandbox/llm-info`. Признаки исправного режима:

```
provider           ollama
llm_reachable      true
embeddings_enabled true
mode               real
```

Контрольный вопрос в разделе «Сима · Студия»: «С какой высоты работы считаются высотными?» Ожидаемый ответ содержит норму **1,3 м** — значение приходит из графа знаний домена, а не из общих знаний модели. Это же проверка Б-02 программы и методики испытаний 11710-11710-51.

Проверка закрытости контура: отключить сетевое соединение машины и повторить вопрос. Ответ должен быть получен.

#### 3.8.7. Возможные затруднения

| Признак | Причина | Действие |
|---|---|---|
| «Ollama не установлена» | нет исполняемого файла в путях поиска | установить по 3.8.2 или 3.8.3 |
| Ollama не отвечает на порту 11434 | служба не запущена | `ollama serve`; журнал — `logs/ollama.log` |
| `mode` показывает `mock` | модель не отвечает либо имя модели не совпадает | `ollama list` и сверить с 3.8.1 |
| `embeddings_enabled` равно `false` | не загружена `bge-m3` | `ollama pull bge-m3` и перезапустить |
| Ответ приходит очень медленно | недостаточно оперативной памяти, модель считается на процессоре | перейти на облегчённую модель из 3.8.1 |
| Загрузка модели обрывается | закрыт исходящий доступ к `registry.ollama.ai` либо нестабильный канал | повторить `ollama pull` — загрузка возобновляется с прерванного места; при закрытом доступе перенести модели по 3.8.4 |
| После переноса `ollama list` пуст | скопирован только каталог `blobs` | перенести также `manifests` — без него веса не опознаются |

## 4. Проверка программы

### 4.1. Автоматическая проверка серверной части

Запуск для проверяющего — из меню скрипта: `./start.command` (Windows: `start.bat`), пункт **2) Приёмочные испытания** (ядро раздела 4, около 6 минут) либо **3)** (полный комплект, около 20 минут). Прямой вызов, если требуется:

```bash
cd backend
.venv/bin/python -m pytest -q
```

На дату документа набор содержит 666 проверок в 69 наборах (число подтверждается командой `.venv/bin/python -m pytest --collect-only -q`). Проверки выполняются на изолированном каталоге данных и рабочее хранилище не изменяют. Итог прогона (число выполненных и число отказавших) заносится в протокол приёмки.

### 4.2. Проверка клиентской части

```bash
cd frontend
npm run lint     # проверка типов и стиля
npm run test     # модульные проверки
npm run build    # сборка; результат — frontend/dist
```

Сборка обязана завершаться без ошибок: содержимое `frontend/dist` размещается по пути `STATIC_DIR`, и без него перехватывающий маршрут вернёт код 404 с пояснением об отсутствии `index.html`.

### 4.3. Сквозная проверка

```bash
./scripts/e2e-smoke.sh
```

Скрипт поднимает изолированный экземпляр серверной части на отдельном порту и во временном каталоге данных и прогоняет полный цикл: получение перечня регламентов, правка, сравнение версий, публикация, архивирование, восстановление, удаление временных данных. Рабочее хранилище не затрагивается.

## 5. Дополнительные возможности

### 5.1. Пульт источников данных

Раздел интерфейса «Пульт ядра ETL» и эндпоинты `/api/etl/*` (все требуют административного входа) позволяют управлять сбором данных без изменения кода и параметров:

### 6.4. Восстановление хранилища при повреждении

Хранилище — файл `regulations.duckdb` и журнал предзаписи `regulations.duckdb.wal` в каталоге `DATA_DIR`. Типовая причина повреждения — принудительное завершение процесса в момент записи: журнал предзаписи содержит незавершённую запись, и при следующем запуске её воспроизведение прерывается (в журнале — `Failure while replaying WAL file`).

**Защита реализована на четырёх уровнях:**

1. Рабочее состояние не попадает в образ: файл хранилища, каталоги графов, версий и вложений исключены из сборки; в образе только фикстуры и демонстрационные документы.
2. Проверка при запуске неразрушающая: `start.sh` выполняет открытие файла, `SELECT 1` и `CHECKPOINT`, не изменяя данные.
3. Восстановление в два шага. При отказе проверки и наличии журнала предзаписи переименовывается **только журнал** (`regulations.duckdb.wal.broken-<метка>`), после чего проверка повторяется. Если она проходит — данные сохранены, потеряны лишь незавершённые операции последних секунд. Только если и повторная проверка не проходит, переименовывается основной файл (`regulations.duckdb.broken-<метка>`), и хранилище создаётся заново из фикстур.
4. Принудительный сброс журнала при остановке (`backend/app/main.py:107`) — контейнер останавливается с пустым журналом, и следующий запуск обходится без фазы воспроизведения.

**Порядок действий администратора:**

1. Открыть журнал запуска и найти строку об итоге проверки: `==> DuckDB OK (read + checkpoint)` — норма; `==> ✓ Главный DB-файл валиден` — восстановление первым шагом, данные сохранены; `==> ✗ Главный DB-файл тоже повреждён` — хранилище пересоздано.
2. В последнем случае в каталоге `DATA_DIR` остаётся файл `regulations.duckdb.broken-<метка>`. Он не удаляется автоматически и доступен для разбора.
3. Возврат к сохранённому состоянию выполняется в командной оболочке контейнера при остановленном приложении:

```bash
mv /data/regulations.duckdb.broken-<метка> /data/regulations.duckdb
# перезапустить службу
```

4. Если возврат не удаётся, содержимое извлекается из повреждённого файла выгрузкой в режиме только для чтения (`EXPORT DATABASE`) с последующей загрузкой в новый файл; порядок сохраняет первичные ключи.
5. Плановая выгрузка каталога данных: `tar czf backup.tar.gz /data`.

**Принудительный сброс хранилища.** Для возврата стенда к исходному состоянию задаётся `SEED_FORCE_RESET=1`, выполняется **один** запуск, после чего переменная снимается. Текущий файл переименовывается в `regulations.duckdb.obsolete-<метка>` и остаётся на томе; хранилище создаётся заново из фикстур.

Мониторинг по протоколу SNMP не реализован (приложение А.6 технического задания); контроль состояния ведётся служебными адресами, описанными в п. 4.4 настоящего руководства.
