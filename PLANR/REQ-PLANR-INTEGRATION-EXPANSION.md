# РАГРАФ ↔ Plan-R (боевой Айбим): расширение дата-контура под инвестор-демо

**Дата:** 2026-07-01. **Статус:** аналитика (все выводы сверены с кодом РАГРАФ и
реальной поверхностью Plan-R API, разведанной токеном).
**Связано:** [HOWTO-PLANR-API-TOKEN.md](HOWTO-PLANR-API-TOKEN.md) (§10 запись/сидер),
[REQ-ZET-INTEGRATION.md](../REQ-ZET-INTEGRATION.md), [REQ-SIGMA-INTEGRATION.md](../REQ-SIGMA-INTEGRATION.md).

## 1. Резюме

Plan-R — это **система записи** (что случилось + кто отвечает), но она не связывает
отклонение с ответственным и не действует. РАГРАФ надстраивается как **система
действия** поверх тех же 6 GET-эндпоинтов: превращает мёртвые поля витрины (33 из 41
EPS-атрибута не читаются, target-версии выброшены, criticalPath читается плоско) в
адресные задачи с дедлайном и в детерминированные регламенты. Главная идея расширения —
**перестать пересказывать движковый slip и начать самим доказывать цифру от базового
плана (target)**, попутно включив регуляторные gate'ы на живых булевых вехах.

**Топ-3 быстрых победы (все на боевых данных Айбим уже сегодня):**
1. Читать 3 булевы вехи разрешений/ГГЭ → gate-регламенты «нельзя строить/сдавать без
   разрешения» (killer-фича, юридически весомо).
2. Читать EPS-роли (Куратор/PM/руководитель/департамент) → адресная маршрутизация
   задач и уведомлений (вау-эффект: задача/письмо улетает конкретному ответственному).
3. Снять фильтр target в `fetch_aggregates` → настоящий план-факт SPI/CPI (флагман под
   позиционирование «детерминированный верификатор»).

### 2.x target-версии = план-факт / EVM (сейчас игнорируется) ⭐

**Главный разблокировщик.** Подтверждено кодом: `fetch_aggregates` берёт
`actual = [v for v in versions if v.get("status") in ("actual","version")]` — `target`
отбрасывается физически. При этом `/versions` даёт 12 target к 12 actual, каждая target
связана `parentId` с тем же графиком → по каждому графику есть пара «базовый план ↔ факт».

**Что тянуть:** для каждой schedule найти обе версии, сделать 2-й `/wbs?EpsId=<target>`,
сматчить этапы по `code`/`materialPath`.

| Метрика | Формула | Зачем |
|---|---|---|
| SV | factProgress% − planProgress% (по target-датам к сегодня) | отставание, не зависящее от движкового slip |
| BAC/PV/EV/CV | PV=Σ target-cost (target_finish ≤ сегодня); EV=Σ target-cost×factProgress%; CV=EV−cost_fact | освоенный объём |
| SPI/CPI | SPI=EV/PV; CPI=EV/cost_fact | один индекс здоровья объекта |
| Дрейф даты | actual target_finish(…0026) − target-версия finish | тихое перепланирование baseline |

**Инсайт для питча:** overdue сейчас считается от `slip_days`(…0029), который пишет сам
движок (чёрный ящик). Пара target/actual даёт РАГРАФ **собственный детерминированный**
расчёт → прямое подтверждение позиционирования «детерминированный верификатор»
(Imperious Group): «мы не верим на слово движку — сверяем факт с зафиксированным
базовым планом». **Обязателен кеш в снапшот** — пул ~3000 WBS × 2, минуты.

## 3. Новые регламенты

По образцу существующих (`sensor → input → formula → switch(3) → 3 output`), на боевом
Айбим без касок/1С. Формат: id · триггер · вход · пороги · выход/действие · тег.

**3.1 `construction-permit-gate-start` — запрет старта без разрешения** ⭐
триггер: этап с progress>0 при `permitConstruction=false` · вход: `permitConstruction`,
`expertiseGGE`, `activeWorksCount` · пороги: 0→ok, 1-3→warn, ≥4→critical · выход:
monitor → LEYKA ГИП «остановить до разрешения» → эскалация «незаконное строительство,
N этапов» · [реализуемо сейчас]

**3.2 `construction-commissioning-gate` — блок ввода без разрешения на ввод** ⭐
триггер: maxProgress→100% при `permitCommissioning=false` · пороги: <80→ok, 80-95→warn,
≥95→critical · выход: monitor → LEYKA куратору «инициировать разрешение» → эскалация
«готов, юридически не сдаётся» · [реализуемо сейчас]

**3.3 `construction-expertise-gate` — работы без пройденной ГГЭ**
триггер: `expertiseGGE=false` + активные work · пороги: 0/1-3/≥4 · выход: monitor →
LEYKA Куратор+Координатор → эскалация «риск переделок при отрицательном заключении» ·
[реализуемо сейчас]

**3.4 `construction-plan-fact-variance` — план-факт по baseline (EVM-lite)** ⭐ флагман
триггер: новый снапшот пары target/actual · вход: `spi`, `cpi`,
`contractValueMillionRub` · формула: `health=min(spi,cpi)`,
`risk=(1−health)×contractValue` · пороги: ≥0.95→ok, 0.85-0.95→warn, <0.85→critical ·
выход: monitor → LEYKA ГИП «SPI=0.82, отставание от baseline» → эскалация инвестору с
EVM-карточкой · [реализуемо сейчас] (зависит от §2.x)

**3.5 `construction-critical-path-slip` — просрочка именно на критпути**
триггер: этап `criticalPath=true` + overdue>0 · вход: `criticalOverdueDays`,
`contractValueMillionRub` · формула: `impact=criticalOverdueDays×(1+contractValue/200)` ·
пороги: 0/1-7/≥7 · выход: monitor → LEYKA ГИП «критпуть отстаёт, дата ввода под угрозой»
→ эскалация «прогноз срыва финальной вехи» · [реализуемо сейчас]. Отличие от
overdue-stage: только этапы, двигающие дедлайн → меньше шума.

**3.6 `construction-budget-overrun` — перерасход бюджета этапа**
триггер: cost_fact(13)>cost_plan(12) · вход: `overrunPct` · пороги: ≤0/1-15/>15 ·
выход: monitor → LEYKA PM «факт превысил план на Z%» → эскалация Куратору · [реализуемо
сейчас] (cost-поля уже суммируются, регламента нет)

**3.7 `construction-baseline-drift` — тихое перепланирование**
триггер: текущий target_finish(…0026) vs сохранённый/target-версия · вход: `driftDays`,
`driftedStagesCount` · пороги: 0/1-30/≥30 · выход: «baseline сдвинут на N дн по M
этапам» → эскалация «подрядчик переписывает план» · [реализуемо] (нужна история target
в снапшоте)

**3.8 `construction-progress-stall` — застой без формальной просрочки**
триггер: этап active, progress не меняется между снапшотами, overdue ещё 0 · вход:
`progressDeltaPct`, `daysToTarget` · выход: LEYKA «этап стоит, дедлайн через K» → ранняя
эскалация · [реализуемо] (нужна история progress/окно)

## 4. Доставка: LEYKA-задачи + уведомления (почта Plan-R / Макс) и маршрутизация

### 4.1 Кому (матрица «уровень → EPS-атрибут-исполнитель»)

Извлекается из `/eps-attribute-values` по epsId объекта:

| Уровень | Кому (EPS-атрибут) | Когда |
|---|---|---|
| L1 операционный | **Project Manager** (ФИО) | штатное отклонение по срокам/этапу |
| L2 надзор | **ФИО руководителя** объекта | критпуть, просрочка ≥ порога |
| L3 кураторский | **Куратор** + **Координатор** | регуляторный gate (разрешение/ГГЭ), риск ввода |
| L4 портфельный | **Курирующий департамент** | агрегатный риск (дайджест) |

### 4.2 Каналы доставки — почта, Макс (не только задача в LEYKA)

**Установленный факт:** Plan-R API **не отдаёт** пользователей/почту (нет
`/users`,`/mail`,`/notifications`; у проекта из 41 атрибута нет email/телефона — только
ФИО). Plan-R шлёт письма сам (админ-вкладка «ПОЧТА» = SMTP + почты пользователей в
админке), но через публичный API эти адреса недоступны. Значит **«слать в ту же почту»
= завести собственный справочник контактов в РАГРАФ** и слать свои письма/сообщения на
те же адреса (не через почтовую подсистему Plan-R). Ценность: вердикт РАГРАФ (которого
у Plan-R нет) падает в тот же inbox/мессенджер, который ответственный уже читает.

**Что реально сейчас (сверено с кодом):** единственный работающий внешний канал —
задача в LEYKA (`leyka_task_creator.ensure_task` → `POST /api/tasks`). `sms`,
`claim_letter`, `payment_hold`, `escalate_*` в регламентах — декларативные метки
output-нод, реальной отправки нет.

**Нужны три кирпича:**
1. **Справочник контактов РАГРАФ** (свой, т.к. Plan-R не даёт):
   `{ ФИО / роль / project_code(опц.) → email, max_id, phone, space_id }`. Джойн
   `имя из EPS-атрибута → контакт`. Роль даёт рассылку «всем кураторам»/«ГИП объекта X».
2. **Диспетчер уведомлений** с каналами-плагинами: **email** (SMTP/aiosmtplib —
   `SMTP_HOST/PORT/USER/PASS/FROM`), **Макс** (Bot API — HTTP, как Telegram: bot-token +
   `chat_id` получателя из справочника), **LEYKA** (есть), sms (потом). Режим «сухой» без
   кредов — логируем, что отправили бы.
3. **Резолвер получателя в регламенте** — новое output-действие `notify_responsible
   (channel, role)`: получатель = EPS-атрибут (Куратор/ФИО руководителя/департамент) →
   имя → контакт → отправка каналом(ами); фолбэк на LEYKA-задачу, если контакта нет.

### 4.3 Задачи/уведомления демо (title · роль · due · приоритет · триггер)

| # | Title | Роль | Due | Prio | Триггер |
|---|---|---|---|---|---|
| T-1 | `[Разрешения] {объект}: старт без разрешения на строительство` | Куратор | 48 ч | p1 | permit_construction=false + start-этапы |
| T-2 | `[Ввод] {объект}: приближается ввод без разрешения` | ФИО руководителя | 5 дн | p1 | permit_commissioning=false + финиш ≤30 дн |
| T-3 | `[ГГЭ] {объект}: работы без пройденной ГГЭ` | Куратор+Координатор | 72 ч | p1 | expertiseGGE=false + active work |
| T-4 | `[Критпуть] {объект}: просрочка {N} дн «{этап}»` | Project Manager | 24 ч | p1/p2 | criticalPath=true + slip<0 |
| T-5 | `[План-факт] {объект}: «{этап}» отстаёт от target {N} дн` | Project Manager | 48 ч | p2 | actual finish vs **target** finish |
| T-6 | `[Портфель] {департамент}: план компенсирующих мер {объект}` | ФИО руководителя | 48 ч | p1 | max_overdue≥14 И critical_count≥1 |
| T-7 | `[Бюджет] {объект}: факт {X}>план {Y} на {Z}%` | Project Manager | 72 ч | p2 | cost_fact_total>cost_plan_total |
| T-8 | `[Договор] {объект}: статус «{статус}» при активных работах` | Куратор | 5 дн | p3 | project_status≠активный + work в работе |

### 4.4 Чего не хватает в текущем механизме (подтверждено кодом)

- `ensure_task(regulation_id, title, description, priority)` шлёт в LEYKA **только**
  `title/description/priority/status` — **нет** `assignee_id`, `project_id`, `due_date`.
- Output-ноды флоу несут `action/priority/text/label`, но **поля исполнителя нет**.
- Задача создаётся только при `criterion_kind == "task_closed_within_sla"` + output
  `action='leyka_create_task'`.

**Минимум для демо-маршрутизации:** (а) читать EPS-роль по epsId → маппить ФИО на
контакт/LEYKA-user через справочник §4.2.1; (б) расширить `_create_task_async` полями
`project_id/assignee_id/due_date`; (в) due из таблицы 4.3.
**Компромисс, если справочник не готов:** ФИО ответственного в заголовок и первый
комментарий (`→ Ответственный: Иванов И.И. (Project Manager)`), `assignee_id` = владелец
демо-проекта. Адресность видна без правки LEYKA-API.

## 5. Демо-сценарии на боевом Айбим (только реализуемое сейчас)

Событие → регламент → действие → эффект (роль, измеримый эффект).

- **С1 — Работы без разрешения** (killer): permit_construction=false + start-этапы →
  `permit-gate-start` → T-1 Куратору + письмо/Макс → **недопущение штрафа ст. 9.5 КоАП
  500 тыс–1 млн ₽** + риска остановки.
- **С2 — План-факт по target**: actual-finish vs target-finish → `plan-fact-variance` →
  T-5 PM → объективный контроль дрейфа от baseline, reaction time −6 дней.
- **С3 — Критпуть горит**: criticalPath=true + slip<0 → `critical-path-slip` → T-4 PM
  **p1** 24 ч → удержанный штраф подрядчику (~50 тыс ₽/день) + сохранение даты ввода.
- **С4 — Портфельный риск адресно**: агрегаты max_overdue≥14 И critical≥1 →
  `portfolio-risk` (уже live) → T-6 руководителю + дайджест департаменту → риск в момент
  возникновения, не в месячном Excel.
- **С5 — Перерасход бюджета этапа**: cost_fact>cost_plan → `budget-overrun` → T-7 PM →
  раннее решение по удорожанию.
- **С6 — Ввод без разрешения на ввод**: финиш ≤30 дн + permit_commissioning=false →
  `commissioning-gate` → T-2 руководителю → недопущение простоя готового объекта
  (замороженный капитал 170–1800 млн ₽).
- **С7 — ГГЭ не пройдена, работы идут**: expertiseGGE=false + active work →
  `expertise-gate` → T-3 Куратор+Координатор → недопущение переделок конструктива.
- **С8 — Позитивный контур**: просроченный этап вернулся в норму (slip≥0) →
  `sensor_returned_normal` → авто-закрытие связанной задачи + обновление risk_score →
  100% прозрачность жизненного цикла риска.

## 7. Риски и ограничения (что НЕЛЬЗЯ и как обойти)

- **Нельзя писать даты/slip этапа** — обход: свой расчёт от пары target/actual (§2.x),
  не пишем в Plan-R. [ограничение API]
- **Нельзя выставить status='actual'** — обход: whitelisting 'version' в pull уже сделан.
- **Нет `/users`,`/mail`,`/resources`,`/documents`,`/costs`,`/risks`,`/calendars`,
  `/tasks`,`/milestones`** — обход: исполнитель из EPS-ролей (ФИО) + свой справочник
  контактов (§4.2); чего нет в API — не обещать в демо. [ограничение API]
- **`/wbs-relations`=405** — обход: дерево из materialPath/level/indexNumber.
- **Тяжёлый пул ~3000 WBS × 2 (с target), минуты** — обязательный кеш в снапшот.
- **`/eps-attribute-values` не tenant-scoped** — джойнить строго по своим epsId (уже так).
- **`contract_value_million_rub` — прокси** из cost_plan (реального поля «Сумма договора»
  нет) — помечать в UI как оценку.
- **Каски/1С — только в моке** — боевое демо строим только на 6 GET; ppe/material не
  показывать на боевом Айбим. [нужен доп. датчик вне Plan-R]

**Feature-request к команде Plan-R** (их gap'ы, не наши): запись дат/slip этапа;
выставление status='actual'; endpoint-словарь WBS-атрибутов; справочник имён для UUID
ресурсов; `/wbs-relations`; tenant-scoping значений атрибутов; **экспорт/эндпоинт
пользователей с email/ролями** (для сквозной маршрутизации уведомлений).
