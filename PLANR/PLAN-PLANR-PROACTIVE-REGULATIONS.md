**Дата:** 2026-07-04. **Идея (Олег):** кроме диалогового агента (руководитель СПРАШИВАЕТ) —
чтобы **ИИ САМ** обнаруживал риски и **напоминал/пушил** сотрудников стройки: снижать простои и
штрафы за позднюю сдачу ДО того, как они случились.
**Связано:** [REQ-PLANR-INTEGRATION-EXPANSION.md](REQ-PLANR-INTEGRATION-EXPANSION.md) (описания

## 1. Реактив → Проактив

- **Реактив (есть):** диалоговый аналитик — руководитель спрашивает, агент отвечает по данным.
- **Проактив (строим):** на КАЖДОМ pull регламенты-детекторы прогоняются по свежим данным; при
  срабатывании РАГРАФ САМ шлёт адресный вердикт ответственному (Telegram/задача LEYKA) — «этап X
  отстаёт, дедлайн через N дней, прими меры». Руководителя не ждём.

Ядро уже есть: авто-уведомление при ухудшении (P1-A, дайджест по bindings). Нужно: **больше
регламентов-детекторов** + **адресность** (кому) + **упреждающие напоминания** (до дедлайна).

## 2. Регламенты-детекторы (2 боевых + 6 новых)

Боевые: `construction-overdue-stage` (контроль сроков), `construction-portfolio-risk` (портфельный
риск). Новые (описания и пороги — REQ-EXPANSION §3):

| Регламент | Триггер | Проактивный эффект |
|---|---|---|
| **permit-gate-start** ⭐ | старт этапа без разрешения на строительство | стоп «незаконное строительство» → штраф ст. 9.5 КоАП |
| **commissioning-gate** ⭐ | приближается ввод без разрешения на ввод | не заморозить готовый объект |
| **expertise-gate** | активные работы без пройденной ГГЭ | не допустить переделок конструктива |
| **plan-fact-variance** ⭐ | SPI/CPI падает vs baseline (нужны target-версии) | раннее «объект отстаёт от плана» |
| **critical-path-slip** ✅ | просрочка именно на критпути (criticalPath=true) | защита даты ввода, штраф подрядчику ~50 тыс ₽/день |
| **budget-overrun** ✅ | cost_fact > cost_plan этапа | раннее решение по удорожанию |

Зависимости данных: permit/commissioning/expertise — п.3 [ТЗ Plan-R](REQ-PLANR-TEAM-DATA-SPEC.md);
plan-fact — target-версии (п.4); critical-path/budget — данные уже есть.

## 3. Упреждающие напоминания (не по нарушению, а ЗА N дней)

Детекторы «раннего предупреждения» на каждом pull (не ждут просрочки):

- **Дедлайн близко:** этап с финишем ≤7 дн и факт < X% → «не успеваете, ускорьте».
- **Критпуть под угрозой:** критпуть-этап замедляется (progress не растёт между pull) → ранняя эскалация.
- **Разрешение к старту/вводу:** объект приближается к вехе, а разрешение отсутствует → «оформить заранее».
- **График устарел:** не пересчитывали > 60 дн (Q2) → «актуализируйте график, картина искажается».
- **Застой (progress-stall):** этап active, progress не меняется, просрочки ещё нет → ранний сигнал.

## 4. Адресность (кому пушить)

- **Сейчас:** дайджест по bindings пространства (канал Telegram/MAX).
- **Нужно:** маршрут по ответственному объекта — EPS-роль (Куратор/ГИП/PM) → контакт. Требует
  `/users` с контактами (п.2 [ТЗ Plan-R](REQ-PLANR-TEAM-DATA-SPEC.md)); до этого — свой справочник
  `planr-contacts.json` + ФИО в заголовок задачи (компромисс REQ-EXPANSION §4.4).

## 6. Механика (переиспользуем существующее)

`puller` (pull per-space) → регламенты (Flow DSL, `regulation_store`) фаерят по свежим works →
дедуп состояния (`planr_notify_state`, как в P1-A, без спама) → доставка по bindings/контактам
(`telegram_notifier`/`leyka_task_creator`). Всё детерминированно; LLM — только для формулировки
текста уведомления (числа из кода, как в агенте).
