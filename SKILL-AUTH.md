# SKILL: Auth & Access Management (Redmine-Style) for NSU AI Center

## 1. Контекст проекта (Project Context)
Вы — Senior Security/Backend Engineer. Ваша задача — спроектировать подсистему аутентификации и авторизации (RBAC) для таск-трекера. 
Требования: максимальная простота для пользователя (вход в один клик через Mail.ru / VK ID) и прозрачная административная панель в стиле Redmine (матрица прав и проектные роли) без переусложненных энтерпрайз-решений вроде Keycloak.

## 2. Технологический стек аутентификации (Auth Stack)
- **Backend:** FastAPI + JWT (JSON Web Tokens). Хранение токена в `HttpOnly Secure` куках для защиты от XSS.
- **OAuth2 Клиент:** Интеграция с OAuth2-провайдером (Mail.ru / VK / Yandex) через библиотеки `Authlib` или `httpx`.
- **Middleware:** Использование Dependency Injection в FastAPI (`Depends`) для проверки прав на уровне эндпоинтов.

## 3. Логика аутентификации (Вход в систему)
1. **SSO Login:** На экране входа единственная кнопка «Войти через Mail.ru» (или корпоративный портал). При первом входе система автоматически создает профиль пользователя в таблице `Users`, но дает ему минимальные права (Гость/Ожидает подтверждения).
2. **Local Admin:** Оставить один сервисный root-аккаунт (логин/пароль), который зашит в переменных окружения (`.env`) на случай падения внешнего SSO-провайдера.

## 4. Ролевая модель (Как в Redmine - Authorization)
Управление правами должно быть двухуровневым: Глобальные права и Проектные роли.

### 4.1. Глобальный уровень (Global Roles)
Флаг в таблице `Users`: `is_superuser` (boolean).
- **Администратор (Superuser):** Видит все проекты, может создавать новые проекты, добавлять Партнеров, назначать глобальные роли.
- **Обычный пользователь:** Видит только те проекты, в которые его добавили.

### 4.2. Уровень проекта (Project-level Roles - Наследие Redmine)
Создайте связующую таблицу `ProjectMembers` и справочник `Roles`. Человек может быть "Менеджером" в проекте "РТК", но обычным "Наблюдателем" в проекте "Альфа-Банк".

- **Таблица `Roles` (Справочник ролей):** 
  - Поля: `id`, `name` (Менеджер, Разработчик, Заказчик/Наблюдатель).
  - Поля-разрешения (boolean): `can_edit_tasks`, `can_manage_budget`, `can_delete_comments`, `can_move_status`.
- **Таблица `ProjectMembers` (Матрица доступа):**
  - Поля: `project_id`, `user_id`, `role_id`.

## 5. Админ-панель (UI для управления доступом)
Интерфейс выдачи прав должен быть визуально скопирован с лучших практик Redmine:
1. **Вкладка "Участники" внутри настроек Проекта:** 
   - Таблица из трех колонок: [Пользователь] | [Роль] | [Действия].
   - Форма добавления: Выпадающий список пользователей -> Чекбоксы ролей (можно назначить сразу несколько, например: Разработчик + Тестировщик) -> Кнопка "Добавить".
2. **Глобальная вкладка "Роли и Разрешения" (Только для Админов):**
   - Классическая "шахматка" (матрица). По вертикали — список всех возможных действий в системе (Создание задачи, Изменение дедлайна, Просмотр бюджета). По горизонтали — названия Ролей (Менеджер, Инженер, Гость). На пересечении — галочки (чекбоксы).

## 6. Защита API-эндпоинтов (Backend Rules)
При написании эндпоинтов в FastAPI, создайте удобный декоратор (Dependency), который проверяет права "на лету":

# Пример целевого стиля кода:
@router.patch("/projects/{project_id}/tasks/{task_id}")
async def update_task(
    project_id: int, 
    task_id: int,
    user: User = Depends(get_current_user),
    has_access: bool = Depends(require_permission("can_edit_tasks"))
):

# Если прав нет, require_permission автоматически выбросит 403 Forbidden pass

Это гарантирует, что разработчик не забудет проверить права при добавлении новой функции.
