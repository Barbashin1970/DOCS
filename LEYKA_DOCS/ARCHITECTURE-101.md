# ARCHITECTURE-101.md — Архитектура LEYKA для новичков

> **Аудитория:** аналитик, тестировщик, новый разработчик, заказчик с техническим минимумом.
> **Цель:** объяснить устройство системы простыми аналогиями, не теряя при этом конкретики LEYKA — какие endpoint'ы, какие поля, какие ошибки в логах что значат.
> **Если нужна формальная архитектура** — смотри [`ARC.md`](ARC.md). Этот документ — мостик к нему.

---

## 1. Большая картинка: LEYKA — это ресторан

Представь систему как ресторан:

| Часть LEYKA | Аналогия в ресторане | Что физически происходит |
|---|---|---|
| **Frontend** (браузер пользователя) | Зал с официантами и меню | React рисует кнопки и формы, ловит клики |
| **Backend** (FastAPI на Railway) | Кухня с поварами | Python принимает запросы, проверяет права, считает KPI |
| **База данных** (SQLite-файл) | Холодильник с полками | Таблицы `users`, `tasks`, `projects`, `comments` |

Когда менеджер двигает задачу из «In Progress» в «Done», происходит вот что:

```
Зал (React) → Окошко выдачи (HTTP API) → Кухня (FastAPI) → Холодильник (SQLite)
       ←────────────── Готовое блюдо (JSON) ──────────────────────
```

Все три слоя живут отдельно: фронт — на Vercel, бэк — на Railway, база — в файле `/data/leyka.db` на диске Railway. Связаны между собой только HTTPS-запросами и SQL-запросами.

## 2. Backend: кухня

### 2.1 FastAPI — стойка приёма заказов

**Что это.** Python-фреймворк для построения HTTP API. Ты описываешь маршруты (URL), а Python отвечает на запросы JSON-ом.

**Аналогия.** Стойка приёма заказов на кухне. Каждый endpoint (`GET /tasks`, `POST /projects`, `PATCH /tasks/{id}`) — отдельное окошко на стойке. Пришёл заказ → повар обработал → блюдо выдали.

**Зачем `async`.** Обычный Python ждёт: «спросил БД → сижу жду → ответ пришёл → пошёл дальше». Слово `async/await` позволяет официанту, пока повар готовит, обслуживать другие столики. Для LEYKA это критично: один HTTP-запрос к базе занимает 5–50 мс, и без async один пользователь блокировал бы весь сервер.

**Что видит тестировщик.** FastAPI автоматически генерирует Swagger UI по адресу [`/docs`](https://leyka-nsu-backend.up.railway.app/docs) — там все ~80 endpoint'ов LEYKA с формами. Можно нажать «Try it out», вбить параметры и посмотреть живой ответ. Это и есть первый инструмент ручного тестирования API.

```text
GET  /healthz                  → {"status": "ok"}
GET  /api/v1/projects          → [{"id": "...", "name": "..."}, ...]
POST /api/v1/tasks             → создать задачу, вернуть JSON с id
PATCH /api/v1/tasks/{uuid}     → обновить поле, вернуть обновлённый объект
```

### 2.2 Pydantic — контракты на форматы

**Что это.** Идёт в комплекте с FastAPI. Ты декларируешь: «у задачи должно быть `title` (строка), `status` (одно из 5 значений), `due_date` (дата или null)».

**Что происходит при нарушении.** Если фронт прислал `due_date: "вчера"`, FastAPI автоматически вернёт `422 Unprocessable Entity` ещё до того, как запрос дойдёт до бизнес-логики. Это очень дешёвая защита от мусора на входе.

**Для аналитика.** Pydantic-схемы в `backend/app/schemas/` — это, по сути, документация требований в коде. Если непонятно, какие поля принимает `POST /tasks` — открой `schemas/task.py` и увидишь точный контракт.

### 2.3 SQLAlchemy 2 async — переводчик в холодильник

**Что это.** ORM (Object-Relational Mapper) — переводчик между Python-объектами и SQL-таблицами. Вместо «руками» писать `SELECT * FROM tasks WHERE project_id = 5`, ты пишешь:

```python
tasks = await db.execute(
    select(Task).where(Task.project_id == project_id)
)
```

SQLAlchemy сам сгенерирует SQL, выполнит запрос и вернёт список Python-объектов `Task`.

**Аналогия.** Повар не лезет в холодильник руками за каждым ингредиентом — он говорит кладовщику «дай 2 яйца», а тот знает, на какой полке что лежит. SQLAlchemy — это и есть кладовщик.

**Версия 2 и `async`.** В SQLAlchemy 2 ORM умеет работать асинхронно — не блокировать сервер, пока ждёт ответа от диска. Это критично для FastAPI: если запросы к БД блокирующие, весь async-стек теряет смысл.

**Что видит тестировщик в логах.** Две частые ошибки:
- `IntegrityError` — нарушение ограничения БД (попытка создать второго пользователя с тем же email; ссылка на несуществующий `project_id`);
- `DetachedInstanceError` — код попытался обратиться к объекту уже после закрытия сессии (баг в коде, не в данных).

### 2.4 Alembic — git для структуры таблиц

**Что это.** Система версионирования схемы БД. В LEYKA — 27 файлов миграций (`0001_initial.py`...`0027_...py`), каждый описывает: «добавить столбец», «создать таблицу», «добавить индекс».

**Зачем.** Если просто поменять модель SQLAlchemy в коде, реальная база не обновится — нужен `alembic upgrade head`. Это первое, что делает `start.sh` при старте сервера на Railway.

**Что видит тестировщик.** Если после деплоя API падает с `column "xxx" does not exist` — значит, код ушёл вперёд, а миграция не применилась. Проверка: `alembic current` (какая версия применена) vs `alembic heads` (какая последняя в репо).

### 2.5 SQLite + WAL — встроенный холодильник

**Что такое SQLite.** Файловая база данных — вся БД живёт в одном файле `/data/leyka.db`. Никакого отдельного сервера БД нет. Удобно для деплоя: одна переменная `DATABASE_URL`, один файл, легко бэкапить (`cp leyka.db backup.db`).

**Аналогия.** PostgreSQL — это большой промышленный холодильник в отдельной комнате, к нему нужно подключаться по сети. SQLite — холодильник прямо на кухне, встроенный в стену. Для центра ИИ НГУ с командой 10–50 человек этого достаточно (см. обоснование в [`SKILL-INFRA.md`](SKILL-INFRA.md)).

**Зачем WAL (Write-Ahead Log).** Стандартный режим SQLite при записи блокирует файл целиком — пока один пишет, остальные ждут. В режиме WAL изменения сначала попадают в отдельный файл-журнал (`leyka.db-wal`), а в основной файл переносятся позже. Эффект:

| Ситуация | Без WAL | С WAL |
|---|---|---|
| Менеджер сохраняет задачу | Блокирует БД полностью | Пишет в журнал, не блокирует |
| Директор одновременно смотрит KPI | Получает «database is locked» | Читает основной файл спокойно |
| Сервер упал в момент записи | Частичные данные, риск повреждения | Журнал откатывается, данные целы |

**Что видит тестировщик.** Ошибка `database is locked` в логах = WAL не включён или несколько процессов пытаются писать одновременно без очереди. В LEYKA с одним worker'ом и aiosqlite это практически исключено.

## 3. Frontend: зал

### 3.1 React — конструктор из компонентов

**Что это.** Библиотека для построения UI из переиспользуемых блоков. Каждый компонент — функция, возвращающая HTML-разметку. `<TaskCard />`, `<KpiTile />`, `<Sidebar />` — это всё компоненты LEYKA.

**Аналогия.** Зал ресторана собирается из стандартных блоков: столики, стулья, меню на стойке. Компоненты React — такие «кирпичики», которые переиспользуются. `<TaskCard />` рисуется одинаково и на доске проекта, и в результатах поиска, и в Inbox — код один.

**Что видит тестировщик.** Если карточка задачи везде в системе ведёт себя одинаково — это не случайность, а один и тот же компонент. Баг в одной карточке = баг во всех. Зато и фикс — в одном месте.

### 3.2 TypeScript — JavaScript с контрактами

**Что это.** Надстройка над JavaScript, добавляющая типы. Если в ТЗ сказано «у задачи статус — одно из 5 значений», TypeScript закрепляет это в коде:

```typescript
type TaskStatus = 'inbox' | 'in_progress' | 'review' | 'done' | 'cancelled';
```

Если разработчик случайно напишет `status: 'finished'` — компилятор выдаст ошибку ещё до запуска приложения.

**Что это значит для тестировщика.** Целый класс багов («неожиданное значение поля», «опечатка в названии статуса», «забыл новое поле в форме») отлавливается ещё до сборки. Команда `npm run typecheck` в CI — это бесплатная статическая проверка, которая ловит то, что иначе пришлось бы тестировать руками.

### 3.3 Tailwind CSS — конструктор стилей

**Что это.** Библиотека CSS-утилит. Вместо написания отдельных `.css` файлов, классы пишутся прямо в HTML:

```html
<div class="bg-blue-500 rounded-lg p-4 text-white font-bold">
```

**Аналогия.** Обычный CSS — это шить костюм с нуля. Tailwind — это конструктор: берёшь готовые детали (`синий фон`, `скруглённые углы`, `отступ 4`), собираешь нужный вид.

**Что это значит для аналитика.** Цвета KPI-плиток (красный для просрочки, зелёный для выполнения) — это классы вроде `bg-red-500`, `bg-emerald-600`. Если нужно поменять порог цвета — ищи в коде условие `if (progress < 0.3)`, а не правь CSS-файл. Бизнес-логика и стили живут в одном месте.

### 3.4 TanStack Query — память официанта на заказы

**Что это.** Библиотека управления данными с сервера. Когда компонент React хочет список задач, он не делает `fetch` руками — он объявляет:

```typescript
const { data: tasks, isLoading } = useQuery({
  queryKey: ['tasks', projectId],
  queryFn: () => api.getTasks(projectId),
  staleTime: 15_000,  // данные «свежие» 15 секунд
});
```

TanStack Query сам: делает запрос, кэширует результат, показывает `isLoading: true` пока грузится, автоматически обновляет при возврате на вкладку, повторяет при ошибке сети.

**Аналогия.** Официант помнит заказы столиков. Если стол 5 спросил меню 10 секунд назад — он отдаст из памяти, не побежит на кухню снова. Но если прошло 15 секунд или меню могло поменяться — побежит уточнить.

**Что это значит для тестировщика.** Баг «счётчик в шапке доски не обновился» — это часто кэш TanStack Query (в LEYKA `staleTime` для счётчиков — 15 секунд). Это **не баг, а дизайн-решение**: лучше показать чуть устаревшее число мгновенно, чем грузить страницу 200 мс. Когда тестируешь real-time обновления, учитывай `staleTime` и поведение `refetchOnWindowFocus`.

**Мутации.** Когда пользователь создаёт задачу — это `useMutation`:

```typescript
const createTask = useMutation({
  mutationFn: (data) => api.post('/tasks', data),
  onSuccess: () => {
    queryClient.invalidateQueries(['tasks', projectId]);
    // ↑ помечает кэш «протухшим», список перезапросится автоматически
  },
});
```

**Optimistic update** (в LEYKA — для drag&drop задач, лайков на wiki, переключения видимости): UI обновляется мгновенно до ответа сервера. Если сервер вернул ошибку — UI откатывается назад. Тестовый сценарий: «сервер вернул 500 → откатился ли UI обратно?»

### 3.5 Zustand — мысли официанта в голове

**Что это.** Минималистичное глобальное хранилище UI-состояния. Если TanStack Query отвечает за «данные с сервера», то Zustand отвечает за «чистое UI-состояние»:

- свёрнут ли сайдбар (`isSidebarCollapsed`);
- какие обои стола выбраны (`wallpaperId`);
- какие фильтры активны на доске (`selectedKind`).

**Аналогия.** TanStack Query — блокнот официанта с записанными заказами от кухни (данные). Zustand — это то, что официант держит в голове: «сейчас обслуживаю столик 3, меню раскрыто, клиент смотрит на десерты» (UI-состояние).

**Почему не просто `useState`.** `useState` — локальная память одного компонента. Если нужно, чтобы и сайдбар, и шапка, и доска одновременно знали «панель свёрнута» — проще иметь одно глобальное хранилище, чем «прокидывать пропсы» через 10 уровней вложенности компонентов.

## 4. Полный путь одного клика: от UI до БД

Что происходит, когда менеджер перетаскивает задачу в колонку «Done»:

```
1. [React UI]          Пользователь отпускает карточку в новой колонке.
        ↓
2. [Zustand / RQ]      Optimistic update: карточка визуально мгновенно
                       встаёт в «Done» (никто не ждёт сервер).
        ↓
3. [TanStack Query]    useMutation отправляет: PATCH /api/v1/tasks/{uuid}
                       Body: {"status": "done"}
        ↓
4. [FastAPI Router]    Принимает запрос. Dependency get_current_user
                       читает JWT-cookie, находит пользователя.
        ↓
5. [Pydantic]          Валидирует: "done" — допустимое значение
                       TaskStatus enum? Если нет → 422 сразу.
        ↓
6. [RBAC Dependency]   Проверяет: у пользователя есть can_edit_tasks
                       в проекте этой задачи? Если нет → 403.
        ↓
7. [SQLAlchemy async]  SELECT task WHERE id=uuid → UPDATE status='done'.
                       Триггер @event.listens_for создаёт запись
                       в task_status_history с (old, new, user, timestamp).
        ↓
8. [SQLite WAL]        Запись идёт в leyka.db-wal, не блокирует читателей.
        ↓
9. [FastAPI]           Возвращает 200 OK + обновлённый JSON задачи.
        ↓
10. [TanStack Query]   onSuccess: invalidateQueries(['tasks', projectId])
                       → счётчики колонок и связанные виды обновляются.
        ↓
11. [React UI]         Re-render с актуальными данными. Если шаг 9
                       вернул 4xx/5xx → optimistic update откатывается.
```

Если на любом шаге что-то идёт не так — система корректно откатывается, а в логах остаётся `request_id`, по которому можно за минуту найти полный traceback (см. правило 7 в [`STARTING-A-PROJECT.md`](STARTING-A-PROJECT.md) §3.1).

## 5. Шпаргалка: симптом → где смотреть

| Симптом | Где причина | Что это значит |
|---|---|---|
| Данные не обновились сразу после изменения | TanStack Query, `staleTime` | Норма, кэш до 15 сек. Не баг |
| UI обновился, но после F5 откатился | Optimistic update + ошибка мутации | Сервер вернул 4xx/5xx, фронт корректно откатился |
| `422 Unprocessable Entity` | Pydantic-схема | Неверный тип или значение поля. Смотреть `body.errors[]` в ответе |
| `403 Forbidden` | FastAPI RBAC dependency | Нет прав по проектной роли. Проверить ProjectMember |
| `409 Conflict` | SQLAlchemy IntegrityError | Нарушение уникальности (email, username) или FK |
| `database is locked` | SQLite / WAL | Конкурентная запись. На проде с 1 worker почти невозможно |
| Swagger `/docs` не загружается | FastAPI не запустился | Смотреть `journalctl -u leyka-backend` или Railway logs |
| Карточка рендерится с пустым списком | TanStack Query `isLoading: true` | Запрос ещё не вернулся, нормально |
| `column "xxx" does not exist` | Alembic | Миграция не применилась после деплоя |
| Счётчик в Inbox показывает старое число | TanStack Query staleTime | Ждать 15 сек или хард-рефреш страницы |
| Карточка выглядит «по-другому» в одном месте | React-компонент или его проп | Смотреть, какой prop variant передан |
