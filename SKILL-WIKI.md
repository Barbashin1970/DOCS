Управление знаниями и проектной документацией (тем более по строгим стандартам вроде ГОСТ 34 и ЕСПД 19) — это половина успеха в разработке ИИ-систем. Подход с Markdown (как в GitHub) идеально подходит для технарей, а древовидная структура (как в Confluence) даст нужный порядок.

## 1. Контекст проекта (Project Context)
Вы — Senior Fullstack Engineer, эксперт по системам управления знаниями (DMS). Ваша задача — спроектировать модуль «База знаний / Wiki» внутри таск-трекера. 
Модуль должен стать единым окном правды для проектной документации, технического заданий (ТЗ), регламентов, архитектурных решений (ADR) и договоров. Ожидается строгое версионирование, поддержка сложного форматирования (под ГОСТ/ЕСПД) и гранулярный ролевой доступ.

## 2. Технологический стек модуля (Wiki Tech Stack)
- **Хранение (Backend):** PostgreSQL (тип поля `TEXT` для Markdown).
- **Парсер и Рендер (Frontend):** `react-markdown` с плагинами `remark-gfm` (поддержка сложных таблиц, чекбоксов, сносок как в GitHub) и `rehype-raw` (для кастомного HTML).
- **Редактор (Editor):** Split-view редактор (Monaco Editor / CodeMirror) или WYSIWYG Markdown-редактор (например, Milkdown или TipTap), чтобы нетехнические пользователи (бухгалтеры) могли писать текст без знания синтаксиса.
- **Экспорт:** Генерация PDF-документов для печати по ГОСТ (использование кастомных `@media print` CSS-стилей или серверной генерации через Puppeteer/WeasyPrint).

## 3. Архитектура данных (Database Schema)
Для реализации древовидной структуры документов (как в Confluence) используем паттерн Adjacency List (список смежности) и версионирование:

- **Таблица `WikiPages` (Страницы):**
  - Поля: `id`, `project_id` (FK), `parent_page_id` (FK -> WikiPages.id для создания дерева/папок), `title`, `content_md` (сам Markdown-текст), `access_level` (уровень доступа).
- **Таблица `WikiPageVersions` (История изменений):**
  - Поля: `id`, `page_id`, `content_md`, `author_id`, `created_at`, `commit_message` (что изменили).
  - *Правило:* Каждое сохранение страницы создает новую версию. Должна быть кнопка "Сравнить с предыдущей" (Diff/History).
- **Таблица `WikiAttachments` (Вложения):**
  - Файлы (сканы актов, схемы Visio/Draw.io), прикрепленные к конкретной странице.

## 4. Ролевая модель доступа к документам (Document RBAC)
Модуль должен интегрироваться с правами из `SKILL-AUTH.md`. Доступ ограничивается на уровне дерева страниц через поле `access_category` или `required_role`:

- **Уровень 1: Строго конфиденциально (Финансы / Юристы)**
  - *Примеры:* Договоры, Сметы, Акты, Зарплатные ведомости.
  - *Доступ:* Только Руководитель проекта (PM) и Бухгалтер.
- **Уровень 2: Внутренняя кухня (Команда разработки)**
  - *Примеры:* Архитектурные схемы, ТЗ, Протоколы совещаний (Meeting Notes), логи паролей к серверам.
  - *Доступ:* Вся внутренняя команда ЦИИ (Разработчики, Менеджеры, Аналитики). Заказчик этого не видит.
- **Уровень 3: Публичные проектные документы (Внешние)**
  - *Примеры:* Руководство пользователя (ЕСПД 19), Руководство администратора, API-контракты, Релиз-ноуты.
  - *Доступ:* Чтение доступно всем участникам проекта, включая внешних Заказчиков/Наблюдателей (МТС, РТК).

## 5. UI/UX Паттерны Базы Знаний
Интерфейс должен быть сфокусирован на чтении больших объемов текста:
1. **Трехпанельный Layout:**
   - *Левая панель:* Дерево страниц проекта (Tree View) с возможностью перетаскивания страниц друг в друга (вложенность).
   - *Центр:* Сам документ с хорошей типографикой (ширина строки не более 80-90 символов для комфортного чтения, интерлиньяж 1.5-1.6).
   - *Правая панель:* Автоматически генерируемое Оглавление (Table of Contents - TOC), собираемое из заголовков `#`, `##`, `###`.
2. **Макросы и Интеграция с Задачами:** 
   - Поддержка вставки ссылок на задачи внутри Markdown (например, при вводе `#104` парсер автоматически превращает это в кликабельный бейдж со статусом задачи из Канбан-доски).
3. **Smart Search:** Полнотекстовый поиск (Full-text search) по содержимому всех Markdown-страниц с подсветкой (highlighting) найденных слов в результатах.

## 6. Требования к ГОСТ / ЕСПД форматам
Поскольку Центр ИИ пишет документацию по стандартам, парсер должен поддерживать:
- Строгую многоуровневую нумерацию (1., 1.1., 1.1.1.).
- Вставку таблиц с объединением ячеек (colspan/rowspan), что иногда требует поддержки HTML-тегов `<table>` внутри Markdown.
- Формализованные титульные листы (выводятся через специальные шорткоды или метаданные YAML/Frontmatter в начале MD-файла).
