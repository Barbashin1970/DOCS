## 0. Коротко

Закрываем «вероятностный уровень» 4-уровневой модели **Д.Е. Пальчунова** (НГУ,
коллега С.С. Гончарова и Д.И. Свириденко). Считаем posterior по правилу Лапласа
по success_rate каждого регламента и показываем точечную оценку + 90% credible
interval. **Фича включается на регламент только после накопления опыта** —
минимум 10 оценённых прогонов, целевая зрелость 20+.

## 1. Контекст: почему вообще

Пальчунов даёт каркас «онтологический / теоретический / прецедентный / вероятностный».
В РАГРАФ первые три уровня **уже работают**:

- **Онтологический:** `*.data.ttl`, sensor_subtype catalog, Domain.
- **Теоретический:** SHACL shapes (фикстуры + редактор), acceptance_criterion kinds.
- **Прецедентный:** `regulation_metrics`, `recent_runs`, `acceptance_resolver`, ТФС-6.
- **Вероятностный:** **раньше дыра** — только сырой `success_rate` как среднее без статистической оценки.

Пользовательский запрос (2026-05-25): «развей концепцию для РАГРАФ — динамическая
картина для 4-уровневой модели». Реализуем минимум сейчас, оставляя задел для роста.

## 2. Математика

β-распределение как сопряжённый prior для Bernoulli:

```
prior:        Beta(α₀=1, β₀=1)      — равномерное (никаких допущений)
после N=k+f:  Beta(α=1+k, β=1+f)    где k = passed, f = failed
posterior mean = α / (α + β) = (1 + k) / (2 + N)
CI [5%, 95%]  = β.ppf(0.05, α, β) ... β.ppf(0.95, α, β)
```

Реализация — pure-Python через `math.lgamma` + continued fraction для I_x(a,b)
(Numerical Recipes 6.4) + бисекция для inverse CDF. Без scipy. Точность 1e-6
— достаточно для UI-аналитики.

## 3. Eligibility gate (порог включения)

**Threshold = 10 decided runs** (passed + failed, без pending).

Обоснование:
- **< 10:** posterior почти не отличим от prior, любая «оценка» — обман. Лучше
  явно сказать пользователю «соберём данные → подключим», чем рисовать число.
- **10–20:** posterior уже отделяется от prior, но CI ещё широкий (~30 п.п.).
  Полезен как ранний сигнал, но не для критических решений.
- **20+:** CI сужается до ~15–20 п.п., можно строить линию экстраполяции
  и принимать управленческие решения «обновить ли регламент».

Backend возвращает `eligible=false` + человекочитаемый `message` со счётчиком
«накоплено X из 10 нужных». UI рендерит прогресс-бар, без числовой оценки.

## 4. Cold start: текущая ситуация

На момент 2026-05-25 **все 30 seed-регламентов имеют 0 прогонов** — `total_runs=0`.
Это нормально: РАГРАФ ещё не в эксплуатации у заказчиков. Поэтому:

1. **Math + endpoint** работают сейчас — чтобы при первом же реальном прогоне
   статистика начала копиться без доработок.
2. **UI до достижения порога** показывает заглушку с прогресс-баром, ссылку
   на этот документ и явный текст «фича доступна после 10+ прогонов».
3. **Заказчики увидят прогноз** на тех регламентах, где они дольше всего
   работают — например, 5–10 «топовых» по частоте срабатываний. Это даёт
   естественную приоритезацию: фича появляется там, где она нужнее всего.

## 5. Открытые вопросы (для согласования с заказчиками)

1. **Считать ли pending (Phase 2 callback'ы) как «не оценено» — или ждать
   их разрешения?** Сейчас pending не входит ни в `passed`, ни в `failed`.
   Это правильно (нет информации = нет учёта), но может затягивать
   достижение порога. Альтернатива — отдельный «pending-aware» режим,
   когда долгие SLA закрываются дефолтным значением.
2. **Per-domain или per-regulation prior?** Сейчас prior=(1,1) одинаковый
   для всех. Можно сделать prior'ом для нового регламента — среднее
   posterior регламентов того же домена. Это даёт смысл «у тепловых
   регламентов исторически 80% успеха» как ожидание для нового тепла.
3. **Окно?** Сейчас агрегат — за всё время. Имеет смысл сделать «за
   последние 90 дней» — чтобы старые runs не доминировали при смене
   физики (новые датчики, новый регламент).
4. **Forecast по другому метрику.** Сейчас только success_rate. Заказчики
   могут попросить: вероятность срабатывания в ближайшие 24 ч, ожидаемое
   число overdue tasks завтра. Это уже не β-распределение; запускаем
   только если будет реальный спрос.

## 6. Что НЕ делается сейчас (зафиксировано как намеренное)

- **Полная 4-квадрантная динамическая картина** (Q1–Q4 на декартовой
  плоскости с осью t, по эскизу пользователя): субъект-управления над
  осью, объект под осью, события как мост, прогноз справа. Идея сильная,
  но дорогая в реализации. Откладываем до подтверждённой полезности
  для заказчиков (запрос «нам нужна вот эта картинка»).
- **Визуальный diff между версиями регламента.** Diff сохраняется
  текстом (`regulation_history.diff_summary` + `diff_counts_json`),
  этого достаточно для аудита. UI с side-by-side рендером Turtle/Flow
  — отдельная большая фича, без запроса не делается.
- **Cox proportional hazards / другие survival models.** Для «времени
  до следующего срабатывания регламента». Сложно, без реального запроса
  нет смысла.
