# LEYKA — инструкция пользователя

**Система управления проектами Центра ИИ НГУ.**
Стек: FastAPI + SQLAlchemy 2 async, React 18 + TypeScript + Tailwind + TanStack Query, SQLite (dev) / PostgreSQL (прод).

Версия на момент написания инструкции — `0.2.0` (виден при наведении на логотип «LEYKA» в шапке сайдбара).

---

## Зачем LEYKA

Центр получает грант Минэка и обязан отчитываться по **11 показателям Приложения №2 Правил экспертизы** (публикации Q1, патенты, внедрения, фреймворки, датасеты и т.д.). LEYKA помогает:

- разложить работу по проектам под конкретных заказчиков и гранты;
- привязать к каждому проекту **обязательства** по этим 11 метрикам;
- собирать **факты достижений** (статьи, патенты, акты) прямо из рабочих задач;
- показывать директору центра **табло KPI** с прогрессом на выбранный отчётный год и подсвечивать, где плана мало, а где уже перевыполнено.

## Доменная модель

```
Partner  ─┐
          ├─→ Project ─→ Task ─→ Comment / Attachment / StatusHistory / Achievement
User  ────┘        └─→ ProjectMember (user + role)
                   └─→ KpiCommitment (metric + target)

KpiCatalog (seed, 11 метрик z-1..z-11)
 └── KpiCenterTarget (план центра на год)
 └── KpiAchievement (факт достижения, привязан к проекту + опц. к задаче/вложению)
```

- **Partner** — заказчик или грантодатель (МТС, Альфа-Банк, ЦИИ НГУ — внутреннее, и т.п.).
- **Project** — инициатива под конкретного партнёра: пре-сейл, активная, на паузе, завершённая, архивная.
- **Task** — единица работы с критерием выполнения, ответственным и стадией на канбане.
- **Comment** — сообщение в ленте задачи с упоминаниями `@` и task-ссылками по UUID.
- **Attachment** — ссылка на внешний документ (Яндекс-диск / Google Docs / GitHub / …) со стадией жизненного цикла.
- **KpiCommitment** — «этот проект обязан закрыть N единиц метрики z-X».
- **KpiAchievement** — «один артефакт = одна запись»: патент, статья, акт, внедрение.

## Роли и что каждый может

> **Два уровня ролей — не путать.**
>
> 1. **Должность сотрудника** (поле `User.role`, у юзера одна на всю систему) —
>    *кто я по работе в центре*: Менеджер, Разработчик, Аналитик, Дизайнер,
>    Куратор, Наблюдатель, Заказчик, Гость. Это **информационный тег** —
>    показывается в карточке профиля и в списке участников. На доступ
>    напрямую не влияет.
> 2. **Проектная роль** (`ProjectMember.role`, у юзера может быть **разная в
>    разных проектах**) — *что мне разрешено в этом конкретном проекте*:
>    Менеджер / Разработчик / Аналитик / Куратор / Наблюдатель / Заказчик.
>    Именно она задаёт permissions: «можно двигать статусы», «можно править
>    бюджет», «можно удалять задачи» и т.д. Матрица флагов настраивается
>    админом на странице *Профиль → «Управление доступом»*.
>
> Списки лейблов **намеренно совпадают** (Менеджер / Разработчик / …),
> чтобы не было визуального диссонанса. Один и тот же сотрудник может быть,
> например, *должность = Менеджер*, при этом в проекте «X» — *проектная
> роль = Разработчик* (потому что в этом проекте он не главный).
>
> Над всем этим — **`is_superuser`** (флаг администратора). Обходит обе
> модели: видит все проекты, может всё. Защищён от само-разжалования
> (последний активный админ не может снять с себя флаг).

### 👑 Директор / Администратор центра (`is_superuser`)

Самый верхний уровень, обходит все RBAC-проверки.

- Видит **все** проекты и задачи, даже не будучи явным участником.
- **Ставит годовой план центра** по каждой из 11 KPI (например, z-9 = 10 статей Q1 на 2026). Экран: «KPI центра» в сайдбаре → клик по метрике → «План по годам».
- **Управляет матрицей прав** (профиль → «Управление доступом») — точечно включает/выключает флаги у ролей: кто может редактировать задачи, удалять, менять состав команды и т.д.
- Удаляет партнёров (каскадом → проекты → задачи).
- Смотрит сводный дашборд центра с цветовыми маркерами: красный = метрика без обязательств («ищи заказчика/грант»), оранжевый = на старте, зелёный = план выполнен, тёмно-зелёный = перевыполнено.

### 📋 Менеджер проекта (роль «Менеджер»)

Полные права внутри своего проекта.

- Создаёт проект под партнёра, редактирует бюджет и сроки.
- Собирает команду (вкладка «Участники» в проекте), назначает роли.
- Создаёт/редактирует/удаляет задачи, двигает по канбану.
- Ставит **обязательства проекта** по KPI (вкладка «KPI» в проекте): «Сигма обязана закрыть 2 внедрения (z-1) и 1 статью Q1 (z-9)».
- Добавляет факты достижений вручную: `+ Факт` на карточке обязательства → заголовок + ссылка на свидетельство Роспатента/страницу статьи.
- Прикрепляет документы (Яндекс-диск, Google Docs, GitHub-ссылки), расставляет стадии.
- Отвечает за критерий выполнения задач — без явного критерия перевод в «Готово» требует подтверждения.

### 💻 Разработчик

Работает с задачами, не управляет составом/бюджетом.

- Видит только проекты, где состоит участником.
- Создаёт, редактирует и двигает задачи.
- Пишет комментарии, прикрепляет документы.
- Отмечает выполнение критериев (двигает в `done`).
- Ставит **@упоминания** коллегам (кнопка `@` справа от скрепки вставит символ и откроет список команды).
- Связывает задачи через UUID (кнопка-идентификатор справа в шапке задачи → «Связанные по смыслу задачи» в другой задаче).

### 📊 Аналитик

Как разработчик, но ориентирован на документацию/ТЗ/отчёты.

- Создаёт задачи и комментирует.
- Прикрепляет ТЗ, исследования, протоколы встреч с правильной стадией.
- Двигает статусы.
- Может редактировать Wiki (этап Wiki — Фаза 2, сейчас только в плане).

### 👀 Наблюдатель

Read-only + комментарии. Для внешних аудиторов/коллег без права влиять на ход работ.

- Видит задачи.
- Может оставлять комментарии.
- Не правит, не двигает, не удаляет, не видит бюджет.

### 🎓 Куратор

Надзорная роль. Подключается к проекту, чтобы **наблюдать за ходом работ** —
видит доску, документы, обязательства по KPI и состав команды, может
комментировать, но ничего не правит и не двигает.

Типовые сценарии, кому даём роль «Куратор» в проекте:

- **Директор центра** — проверяет отчётность по проекту перед сдачей.
- **Директор грантодателя** — контролирует исполнение по грантовому
  соглашению.
- **Главбух НГУ** — сверяет уставы и бюджет, расходование средств.
- **Научный руководитель** — смотрит прогресс исполнителей-аспирантов.
- **Внутренний аудитор** — выборочная проверка проектов центра.

Что видит:

- Все задачи и комментарии.
- Бюджет и его освоение.
- Документы (в т.ч. конфиденциальную Wiki).
- KPI-обязательства и факты.
- Состав команды.

Что НЕ может: создавать/править/удалять задачи, двигать статусы, менять
бюджет, добавлять/убирать людей. Только смотрит и пишет в чат.

### 🏢 Заказчик

Внешний индустриальный партнёр.

- Видит задачи.
- Комментирует.
- Не видит бюджет и конфиденциальное.

> Матрица всех флагов и их точных значений — на странице «Управление доступом» в профиле администратора.

### 🎨 Дизайнер · 👤 Гость

Эти два значения существуют **только как должности** (`User.role`), под них
отдельной проектной роли нет. Дизайнер обычно подключается к проекту с
ролью «Разработчик» или «Аналитик»; «Гость» — статус сразу после первого
входа через OAuth, до того как менеджер примет его в проект.

### Имя пользователя — единое поле

У юзера одно поле `full_name`. Оно изначально приходит от OAuth-провайдера
(Mail.ru/Google) и сразу становится тем именем, которое видят коллеги в
@-упоминаниях, шапках, комментариях. Если SSO прислал ерунду (вроде
`bububu123`), юзер один раз правит имя через **Профиль → «Как меня видят
коллеги»** — и всё. Email привязан отдельно для связи и не правится из UI.

Welcome-задача, которую новичок видит после входа по приглашению, прямо в
чеклисте напоминает: *«Зайди в свой профиль и проверь, как тебя будут
видеть коллеги — поправь один раз или оставь»*.

### Видимость заказчиков и проектов

Поверх ролей есть второй слой — `visibility` у заказчика и проекта:

- **Закрытый** (`private`, по умолчанию) — видят только участники + админ.
- **Открытый** (`public`) — виден всем сотрудникам центра.
- **Демо** (только у проекта) — виден всем включая новичков; безопасен для
  тренировки в онбординге.

Менять видимость может только администратор — переключатель «замок/глобус»
в карточке заказчика и в настройках проекта.

## Жизненный цикл проекта и стадии документов

Проект проходит стадии: **`presale`** (пре-сейл, пока бюджет 0) → **`active`** (в работе) → **`paused`** (приостановлен) → **`completed`** → **`archived`**.

Документы (вложения к задачам) маркируются одной из 12 стадий:

| Slug | Лейбл | Примеры артефактов |
|---|---|---|
| `negotiation` | Переговоры | Коммерческие письма, презентации, протоколы встреч |
| `research` | Исследование | Предпроектные обзоры, аналитика, источники |
| `tor` | Техническое задание | ТЗ, ФТ, ЧТЗ |
| `rnd_research` | Стадия НИР | Отчёты НИР, эксперименты |
| `rnd_dev` | Стадия ОКР | Макеты, схемы, прототипы |
| `user_docs` | Документация пользователя | Руководства по ЕСПД 19 |
| `pmi_testing` | Испытания | ПМИ, протоколы тестов, приёмо-сдаточные |
| `handover` | Сдача заказчику | Акты приёмки |
| `deployment` | Внедрение | Регламенты развёртывания, обучение |
| `remarks` | Замечания | Баг-репорты, списки доработок |
| `support` | Поддержка | Тикеты, FAQ, SLA |
| `reporting` | Отчётность | Отчёты по гранту |

Legacy-slug'и `contract` и `meeting` автоматически маппятся в `research` и `NULL` соответственно — старые записи не теряют лейбл.

### Как считается прогресс

На странице **«KPI центра»** для каждой метрики и выбранного отчётного года показываются три числа:

- **План центра** — суммарная цель, которую директор поставил на год (редактируется из модалки метрики).
- **Взято проектами** — сумма `target_value` по всем `KpiCommitment` на эту метрику во всех проектах.
- **Закрыто** — сумма `value` по всем `KpiAchievement`, у которых `occurred_at` попадает в выбранный год.

Инвариант сводного чипа: **План = В работе + Без обязательств**, где:

- **В работе** = Σ target_total (уже распределено по проектам).
- **Без обязательств** = Σ max(center_target − target_total, 0) — столько единиц плана ещё не раздано, **директор должен назначить ответственных / найти заказчика**.

### Табло-плитки

Вверху страницы — 11 мини-плиток, по одной на метрику. Цвет:

- 🔴 **красный** — `< 30 %` прогресса;
- 🟠 **оранжевый** — `30–70 %`;
- 🟡 **амбер** — `70–100 %`;
- 🟢 **зелёный** — `≥ 100 %` (план выполнен);
- 🟢 **тёмно-зелёный + «+N%»** — перевыполнение свыше `110 %` (например, на 5 статей в плане закрыто 8 → `+60 %`);
- ⚪ **серый** — план не задан.

Подпись под прогресс-баром метрики: `N% выполнено / +N% перевыполнено`. 100 % бара визуально = план центра. Если проекты набрали больше плана, показывается дополнительный светло-зелёный «хвост» справа.

## Типовые сценарии

### Сценарий 1. Новый проект под заказчика

**Менеджер**:
1. Сайдбар → «+ Заказчик» → завести партнёра. Или найти существующего.
2. В карточке партнёра → «+ Добавить проект» → название + стадия (`presale` по умолчанию).
3. Вкладка «Участники» → собрать команду: `+ Добавить` → выбрать пользователя и роль.
4. Вкладка «KPI» → «+ Добавить обязательство» → выбрать `z-X` из списка (с описанием из Приложения №2), поставить `target_value`, комментарий-заметка.
5. Вкладка «Доска» → создавать задачи.

### Сценарий 2. Разработчик закрыл задачу → это факт KPI

**Разработчик**:
1. Открывает задачу на канбане → переводит статус в `done` → подтверждает критерий выполнения.
2. Если результат — документ (акт, свидетельство, статья), прикрепляет ссылку через 📎 → выбирает сервис (Яндекс-диск / Google Docs / GitHub / Задача) → ставит стадию (например, `handover` для акта).

**Менеджер** (или сам разработчик):
3. Вкладка «KPI» в проекте → на нужном обязательстве жмёт `+ Факт` → заполняет заголовок («Акт внедрения МТС по CV-модулю») и ссылку на evidence.
4. Прогресс-бар обязательства двигается.
5. На странице «KPI центра» свод автоматически обновляется.

### Сценарий 3. Директор ставит план на год

**Директор** (superuser):
1. Сайдбар → «KPI центра».
2. Селектор года сверху → выбрать 2026 (или любой в 2024..2100).
3. Клик по строке метрики (например, `z-9` — статьи Q1) → модалка.
4. Секция «План по годам» → напротив `2026` кнопка `+ задать` → ввести `10` → Enter.
5. На дашборде сразу видно: план 10, взято проектами 3, закрыто 1 → цифра «Без обязательств» = `10 − 3 = 7`. CTA на чипе: «Назначь ответственных — распредели по проектам».

### Сценарий 4. Обсуждение и ссылки на другие задачи

**Аналитик** в комментарии:
1. В ленте задачи пишет: «Коллеги, по этапу НИР не закрыты документы в задаче `737fa8d8-...-...`» — UUID копируется кнопкой-идентификатором в шапке нужной задачи.
2. Любой коллега видит в чате кликабельный **TaskChip** `# 737fa8d8… · МТС — задачи` → открывает его во второй вкладке браузера (не теряя текущую).

**Также**: в разделе «Связанные по смыслу задачи» в TaskDrawer можно вручную привязать задачу-источник / задачу-следствие. Это доска-маркер: нарисовал → стёр → нарисовал.

### Сценарий 5. Двойные галочки в ленте

- Под **своим** комментом видны галочки (как в Telegram):
  - ✓ серая — никто из команды пока не прочитал;
  - ✓✓ синяя — кто-то прочитал. Hover → тултип «Прочитали: Олег, Катя».
- При открытии задачи все чужие комменты автоматически помечаются прочитанными (авто-mark-read).
- Если пришли новые комменты, в шапке ленты появляется синяя кнопка **«Прочитать всё»** с числом непрочитанных — один клик сбрасывает «красный хвост».
- Свои комменты в `read_by` не учитываются (ты сам с собой не переписываешься).

### Сценарий 6. Роли и аудит доступа

**Директор**:
1. Клик по карточке профиля справа сверху → **«Управление доступом»**.
2. Таблица: 6 ролей × 12 permission-флагов, сгруппированных на **Задачи / Комментарии / Проект / Wiki**.
3. Клик по галочке — мгновенно меняется флаг роли (optimistic update). Действует тут же во всех проектах, где роль назначена.
4. Не-директор видит эту же страницу как «Мои права» в read-only — полезно, чтобы понять, что ему можно и нельзя.

## Как система учёта превращается в табло

Главный принцип: **KPI центра — это не ручной отчёт, а живой агрегат над реальной работой**.

```
Задачи + Комментарии + Вложения + Статусы
           │
           ▼
     KpiAchievement  ← менеджер/разработчик подтверждает факт через «+ Факт»
           │
           ▼
     Прогресс обязательства проекта  (Σ value / target_value)
           │
           ▼
     Σ по всем проектам + план центра на год
           │
           ▼
     KPI центра (11 плиток + дашборд директора)
```

Нижнее звено (задачи и доки) работает в рамках проекта. Верхнее (директор) работает с агрегатом и годовыми планами. Между ними — `KpiCommitment` (кто взял что) и `KpiAchievement` (что реально сделали).

## FAQ

**Почему у моего проекта в табло 0%, хотя задачи закрываются?** — Потому что задачи закрываются, но `KpiAchievement` никто не создал. Зайди на вкладку «KPI» в проекте и нажми `+ Факт` на нужном обязательстве. Закрытие задачи само по себе KPI-прогресс не двигает.

**Как понять, прочитал ли руководитель мой коммент?** — Под своим комментом в ленте задачи. ✓✓ синими значит прочитал. Наведи — увидишь поимённо кого.

**Почему я не вижу чужие проекты в сайдбаре?** — Потому что ты не superuser. LEYKA показывает не-администратору только те проекты, в которых он явный `ProjectMember`. Чтобы тебя добавили — менеджер идёт на вкладку «Участники» того проекта.

**Что такое «legacy-стадия `contract`»?** — До ревизии списка была стадия «Договор о сотрудничестве», потом мы решили, что договор — это артефакт фазы «Переговоры», а не отдельная стадия. В старых записях slug `contract` автоматически маппится в `research` для отображения.

**Куда смотреть, если нужно найти исполнителя под пустую KPI-метрику?** — В «KPI центра» чип **«Без обязательств»** и красные плитки показывают метрики без распределения по проектам. CTA: «Назначь ответственных — распредели по проектам».
